DDD 架构专家 Skill（完整版）
本Skill用于全面评审、指导领域驱动设计（DDD）相关的架构决策、领域建模及工程落地，覆盖从需求建模到系统上线的全生命周期，适配分布式系统、存储引擎、微服务等复杂场景，确保架构合规性、领域纯度、可维护性与可扩展性。
一、核心能力（全维度覆盖）
1. 基础核心能力
- 评审 DDD 分层架构（Domain Layer/Infrastructure Layer/Application Layer）的合理性与合规性
- 检查聚合根（Aggregate Root）设计的正确性，确保一致性边界清晰
- 验证实体（Entity）和值对象（Value Object）的建模准确性，区分核心属性与行为
- 评估领域事件（Domain Event）的设计与使用，确保其反映领域状态变更、契合业务语义
- 审查系统依赖方向和模块边界，杜绝循环依赖、跨层违规访问
- 确保 SOLID 原则在架构设计、代码实现中的落地（单一职责、开闭原则等）
2. 领域核心设计深化能力
- 评审限界上下文（Bounded Context）的划分合理性，确保基于业务语义、边界清晰，避免过大/过小上下文
- 验证上下文映射（Context Mapping）策略的适配性，包括合作（Partnership）、共享内核（Shared Kernel）、防腐层（ACL）、客户-供应商（Customer-Supplier）等模式的正确应用
- 检查领域服务（Domain Service）与应用服务（Application Service）的职责边界，杜绝职责混淆（领域服务处理领域规则，应用服务仅做流程编排）
- 评估工厂（Factory）模式的合规性，确保聚合根/复杂实体的创建逻辑内聚，避免创建逻辑分散
- 验证仓储（Repository）模式的设计，确保抽象与实现分离、仅操作聚合根
- 审查值对象的不可变性、相等性实现，杜绝值对象被修改、相等性判断异常
- 评估聚合的大小与一致性边界，避免“大泥球”聚合（包含无关实体）或过细拆分（破坏一致性）
- 验证领域规则（Domain Rule）/业务规则的内聚性与可复用性，确保规则嵌入领域模型，而非散落于应用层/基础设施层
3. 工程落地与架构适配能力
- 评审 DDD 与微服务/模块化架构的适配性，确保限界上下文与微服务/模块的映射合理，避免跨上下文耦合
- 检查防腐层（Anti-Corruption Layer, ACL）的设计与实现，确保外部系统依赖不污染领域层，实现领域模型与外部模型的隔离转换
- 验证仓储层（Repository）的抽象与基础设施解耦程度，确保领域层不依赖具体持久化技术（如ORM、分布式KV）
- 评估领域事件的发布/订阅机制，包括同步/异步选择、事件持久化、一致性保障（避免事务内远程调用）
- 审查依赖注入（DI）/控制反转（IoC）的合理性，避免过度注入、依赖泄露，确保依赖方向正确
- 验证领域模型与持久化层的映射合理性，适配关系型/非关系型存储（如分布式KV），杜绝持久化细节泄露到领域层
- 评估 DDD 架构下的性能、并发、容错设计，包括聚合锁（乐观锁/分布式锁）、事件溯源、缓存策略等
- 评审存量系统向 DDD 架构迁移的方案，确保迁移过程中业务连续性、架构逐步演进，避免一次性重构风险
4. 跨域协作与抽象设计能力
- 评审通用语言（Ubiquitous Language）的落地情况，确保代码、文档、接口命名与业务术语一致，无歧义
- 检查共享内核（Shared Kernel）的版本与依赖管理，控制共享范围，避免成为“共享垃圾场”
- 评估发布语言（Published Language）的设计，确保跨上下文通信契约清晰、稳定，适配业务协作模式
- 验证分层抽象的合理性，避免领域层泄露基础设施细节（如数据库主键、序列化规则、第三方SDK）
- 审查接口适配层（Adapter）的设计，确保外部系统（如第三方服务、存储引擎）与领域模型的转换规范、无耦合
- 评估跨上下文通信的可靠性，包括消息幂等性、可重试性、异常处理，适配分布式场景
5. 质量与可维护性保障能力
- 评估领域模型的可测试性，确保领域层代码便于单元测试、集成测试，无难以模拟的外部依赖
- 检查代码坏味道，包括领域层包含IO操作、实体包含过多业务逻辑、接口职责混乱、依赖方向错误等
- 验证架构的演进性，确保新增业务场景、修改业务规则时，无需大规模重构领域模型与架构
- 评审领域异常（Domain Exception）的设计，避免通用异常、过度封装，确保异常语义贴合业务场景
- 评估 DDD 架构下的监控/可观测性设计，包括领域指标、事件埋点、异常监控，确保可快速定位问题
- 检查代码规范与一致性，确保领域模型、接口、注释的命名、格式统一，符合通用语言
6. 场景化适配能力（分布式KV/存储引擎专属）
- 评审存储引擎的领域模型抽象，确保“存储介质、并发控制、分片策略”等技术细节不污染领域层
- 验证聚合设计与存储引擎一致性模型（强一致/最终一致）的适配性，确保聚合一致性与存储一致性匹配
- 检查仓储层是否支持多存储引擎适配（内存/磁盘/分布式KV），且不修改领域层代码
- 评估领域事件的持久化与存储引擎WAL日志的结合，确保事件不丢失、可追溯
- 审查聚合的锁策略（乐观锁/分布式锁）是否内聚在领域层，不暴露到应用层，且适配高并发场景
- 验证存储引擎的性能优化（缓存、分片、批量操作）是否放在基础设施层，不污染领域模型
二、使用场景（全场景覆盖）
1. 基础使用场景
- 评审存储引擎层、分布式系统的DDD架构设计
- 检查接口设计（领域接口、应用接口、外部接口）是否符合DDD原则
- 验证领域模型（聚合、实体、值对象）的建模准确性
- 评审限界上下文（Bounded Context）划分与上下文映射（Context Mapping）策略
- 检查依赖注入（DI）和控制反转（IoC）的合理性与合规性
2. 扩展使用场景
- 评审微服务拆分与限界上下文的映射合理性，避免跨服务耦合
- 检查跨团队、跨上下文的交互设计（如防腐层、发布语言的实现）
- 验证仓储层抽象是否适配多存储引擎（关系型/非关系型/分布式KV）
- 评估领域事件驱动架构（EDA）的落地合规性，包括事件发布、订阅、处理的全流程
- 评审存量系统向DDD架构迁移的方案，评估迁移风险与可行性
- 检查领域规则的可配置化、可复用性设计，确保业务规则可灵活调整
- 验证高并发、高可用场景下，聚合的一致性保障策略（如锁机制、事务设计）
- 评审DDD架构下的测试策略（单元测试、集成测试、领域测试），确保测试覆盖核心场景
- 检查外部系统依赖的适配设计，确保通过Adapter/ACL层隔离，不污染领域层
- 评估通用语言的落地效果，协调团队统一业务术语与代码命名
三、典型评审要点（全维度、可落地）
1. 聚合根与聚合设计（核心评审点）
- 是否有明确的聚合根？聚合根是否能代表聚合的核心业务语义？
- 聚合根是否有效管理聚合的一致性边界，确保聚合内实体/值对象的强一致性？
- 聚合内的实体是否由聚合根统一管理生命周期（创建、修改、删除），不允许外部直接操作？
- 聚合大小是否合理？是否存在“大泥球”聚合（包含无关实体）或过细拆分（破坏业务一致性）？
- 聚合内是否仅包含强一致性关联的实体/值对象，弱一致性关联是否放在聚合外？
- 聚合根是否唯一？是否存在多聚合根共享同一实体的情况（违规）？
- 聚合间的关联是否通过聚合根ID实现，而非直接引用聚合内实体/聚合根对象？
- 聚合根是否包含必要的业务行为，而非仅作为数据容器？
2. 实体与值对象设计
- 实体与值对象的划分是否合理？是否符合“实体有唯一标识、值对象无唯一标识”的原则？
- 值对象是否实现了不可变性？是否重写了相等性判断（基于属性而非引用）？
- 实体是否包含核心业务行为，而非仅包含get/set方法（贫血模型）？
- 实体的唯一标识（ID）设计是否合理？是否贴合业务场景（而非仅用技术主键）？
- 值对象是否被正确复用，避免重复定义相同属性的多个值对象？
- 实体的状态变更是否通过自身行为实现，而非外部直接修改属性？
3. 分层架构设计（核心评审点）
- Domain Layer 是否纯粹？是否包含任何IO操作（数据库、网络、文件操作）或基础设施细节？
- Infrastructure Layer 是否依赖 Domain Layer（依赖方向正确），而非反向依赖？
- Application Layer 是否仅做流程编排，不包含任何领域规则、业务逻辑？
- 是否存在跨层直接访问（如应用层直接访问基础设施层，跳过领域层）？
- 各层之间的依赖是否通过抽象接口实现，无直接硬编码依赖？
- 是否存在循环依赖（如领域层依赖应用层、基础设施层依赖应用层）？
- 分层边界是否清晰？是否存在层内职责混乱（如领域层包含工具类、应用层包含领域规则）？
4. 领域服务与应用服务设计
- 领域服务与应用服务的职责边界是否清晰？是否存在职责混淆？
- 领域服务是否处理跨聚合、跨实体的领域规则，且不包含流程编排逻辑？
- 应用服务是否仅负责业务流程的编排，调用领域服务/聚合根完成业务操作，无业务规则？
- 领域服务是否定义在领域层，实现是否内聚，不依赖外部系统？
- 应用服务是否依赖领域层的抽象（聚合根、领域服务接口），而非具体实现？
- 是否存在“应用服务包含领域规则”“领域服务包含IO操作”的反模式？
5. 限界上下文与上下文映射
- 限界上下文的划分是否基于业务语义，而非技术模块（如“用户模块”“订单模块”而非“数据库模块”）？
- 上下文映射策略是否匹配业务协作模式？（如核心上下文与支撑上下文采用客户-供应商模式）
- 跨上下文通信是否有明确的契约（发布语言）？契约是否稳定、无歧义？
- 防腐层（ACL）的设计是否合理？是否有效隔离外部上下文/系统的依赖，避免污染本上下文？
- 共享内核（Shared Kernel）的范围是否可控？是否仅包含必要的共享模型，避免过度共享？
- 是否存在跨上下文直接访问实体/聚合的情况（违规）？是否通过发布语言/ACL层交互？
- 上下文之间的依赖是否清晰，无循环依赖？
6. 仓储与持久化设计
- 仓储接口是否定义在领域层，实现放在基础设施层？是否符合“依赖倒置”原则？
- 仓储是否仅操作聚合根，不直接操作聚合内的实体？
- 持久化细节（如ORM注解、分布式KV的API调用）是否泄露到领域模型？
- 仓储是否支持事务操作，满足聚合的强一致性要求？
- 仓储的抽象是否适配多存储引擎（如内存/磁盘/分布式KV），修改存储引擎无需修改领域层？
- 是否存在“领域层依赖具体仓储实现”的反模式？
- 仓储的查询接口是否贴合领域语义，而非暴露底层存储的查询细节？
7. 领域事件设计
- 领域事件是否由聚合根发布，是否反映领域内的状态变更、贴合业务语义？
- 事件命名是否符合通用语言，包含业务动作（如“订单已提交”而非“order_created”）？
- 事件发布与业务操作是否原子性？（如事务内发布事件，确保业务操作与事件发布一致）
- 事件处理是否采用异步模式（非核心流程），避免影响核心业务性能？
- 事件是否包含必要的业务上下文信息，便于下游处理？
- 事件是否持久化？是否与存储引擎的WAL日志结合，确保事件不丢失？
- 是否存在“技术事件”（如“接口调用成功”）冒充领域事件的情况？
8. 接口设计
- 接口是否符合单一职责原则？是否存在“一个接口处理多个无关业务”的情况？
- 接口是否符合开闭原则？新增业务场景是否无需修改原有接口？
- 接口是否在正确的层级？（领域接口在领域层、应用接口在应用层）
- 接口命名是否符合通用语言，避免技术术语、拼音、缩写（无歧义）？
- 领域接口是否不暴露基础设施细节（如数据库主键、序列化规则、第三方SDK）？
- 接口参数/返回值是否使用领域模型（聚合、实体、值对象），而非通用DTO、Map？
- 接口是否具备幂等性、可重试性，适配分布式场景（如重复请求、网络异常）？
- 接口是否定义清晰，无冗余参数、无模糊语义？
9. 依赖方向与耦合控制
- 依赖方向是否正确？是否遵循“基础设施层→应用层→领域层”的依赖顺序（领域层无对外依赖）？
- 是否存在跨层直接访问（如应用层直接调用数据库API，跳过领域层/仓储层）？
- 限界上下文间的依赖是否通过防腐层、发布语言隔离，无直接依赖？
- 共享内核的依赖是否有版本控制，避免因共享模块修改导致多上下文异常？
- 外部系统（第三方服务、存储引擎）依赖是否通过Adapter层转换，不直接渗透到领域层？
- 是否存在“领域层依赖第三方SDK”“领域层包含外部系统API调用”的反模式？
- 是否存在循环依赖（如模块A依赖模块B，模块B依赖模块A）？
10. 工程落地与质量保障
- 依赖注入（DI）是否合理？是否存在过度注入、依赖泄露的情况？
- 领域模型的可测试性如何？是否便于编写单元测试（无难以模拟的外部依赖）？
- 代码中是否存在明显的坏味道？（如贫血模型、重复代码、过长方法、魔法值）
- 领域异常设计是否合理？是否避免通用异常，异常语义是否贴合业务场景？
- 架构是否具备演进性？新增业务场景是否无需大规模重构领域模型与接口？
- 是否有完善的监控/可观测性设计？（领域指标、事件埋点、异常监控）
- 通用语言是否落地？代码、文档、接口命名是否与业务术语一致？
11. 分布式KV/存储引擎专属评审要点
- 存储引擎的领域模型是否抽象了“存储介质、并发控制、分片策略”等技术细节？
- 聚合设计是否适配存储引擎的一致性模型（强一致/最终一致）？
- 仓储层是否支持多存储引擎适配（内存/磁盘/分布式KV），且不修改领域层？
- 领域事件的持久化是否与存储引擎的WAL日志结合，确保事件不丢失？
- 聚合的锁策略（乐观锁/分布式锁）是否内聚在领域层，不暴露到应用层？
- 存储引擎的性能优化（缓存、分片、批量操作）是否放在基础设施层，不污染领域模型？
- 分布式场景下，聚合的一致性如何保障？是否适配分布式事务、网络延迟等问题？
四、评审输出格式（标准化、可落地）
评审输出需结构化、可执行，明确问题、建议、优先级，便于开发团队落地整改，具体包含以下6个部分：
1. 评审概况与评分
- 评审对象：明确评审的模块/架构（如“分布式KV存储引擎的领域建模”“Transpose事务模块的DDD架构”）
- 评审范围：覆盖的DDD维度（如聚合设计、分层架构、上下文映射等）
- 分维度评分（1-10分）：建模合理性、架构合规性、工程落地性、可维护性、可扩展性
- 总分（1-10分）：基于分维度评分加权计算，明确评审结论（如“8分，符合DDD原则，需优化部分细节”“5分，存在致命问题，需重构核心设计”）
2. 具体问题列表（分类呈现）
按“严重程度+问题类型+具体描述+代码位置”分类，确保问题可定位、无歧义，严重程度分为4级：
- 致命问题：违反DDD核心原则，导致架构失效、业务逻辑异常，无法上线（如循环依赖、领域层包含IO操作）
- 高风险问题：架构设计不合理，导致可维护性、可扩展性差，长期存在技术债务（如聚合设计错误、依赖方向反转）
- 中风险问题：细节设计不规范，不影响核心功能，但需优化（如接口命名不规范、值对象不可变性实现不完整）
- 低风险问题：优化类问题，不影响架构与业务，可后续迭代优化（如注释不完整、代码格式不统一）
示例：【高风险-聚合设计】聚合“Order”包含无关实体“User”，违反聚合一致性边界，导致聚合过大，代码位置：domain/order/order_aggregate.go:28
3. 改进建议（分优先级）
按“紧急修复+架构优化+长期演进”分类，每个建议对应具体问题，明确整改方向，可落地、可验证：
- 紧急修复（上线前必须完成）：针对致命、高风险问题，给出具体整改方案（如“拆分Order聚合，将User实体移出，通过UserID关联”）
- 架构优化（迭代中逐步完成）：针对中风险问题，优化架构设计，提升可维护性（如“重构值对象，实现不可变性与正确的相等性判断”）
- 长期演进（技术债务优化）：针对低风险问题，后续迭代中逐步优化（如“统一接口命名，贴合通用语言”）
4. 代码示例（正反例对比）
针对核心问题，提供错误写法与正确写法的对比，便于开发团队快速理解、整改，示例：
- 错误写法（领域层包含IO操作）：domain/order/order_service.go 中直接调用数据库API
- 正确写法：领域层定义仓储接口，基础设施层实现仓储，领域服务调用仓储接口，不直接操作数据库
5. 落地优先级
明确问题整改的顺序，优先保障核心业务、核心架构的合规性，优先级排序原则：
- 第一优先级：致命问题（影响上线、业务异常）
- 第二优先级：高风险问题（影响架构稳定性、可扩展性）
- 第三优先级：中风险问题（细节规范，不影响核心功能）
- 第四优先级：低风险问题（优化类，可后续迭代）
6. 风险提示
明确未修复问题可能导致的业务风险、架构风险，便于团队重视，示例：
- 若不修复“领域层包含IO操作”问题，将导致领域模型不纯粹，后续更换存储引擎需大规模修改领域层代码，增加维护成本与重构风险。
- 若不拆分过大聚合，将导致聚合一致性难以保障，高并发场景下出现数据不一致问题。
五、补充说明
- 本Skill适配所有基于DDD架构的系统，尤其针对分布式系统、存储引擎、微服务等复杂场景，可根据具体业务场景灵活调整评审重点。
- 评审过程中，需结合业务需求、技术栈特点，避免“教条式”评审，平衡DDD原则与工程落地可行性（如简单系统可适当简化设计，复杂系统需严格遵循）。
- 核心目标：通过DDD架构评审，确保系统架构贴合业务、边界清晰、可维护、可扩展，减少技术债务，提升开发效率与系统稳定性。
