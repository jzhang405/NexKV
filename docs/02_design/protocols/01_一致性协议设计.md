## 📋 文档概述

本文档详细定义 NexKV 分布式 KV 存储系统的一致性协议设计,包括 Gossip 协议、Quorum 机制和无协调者简化版 2PC 协议。

### 核心设计理念

**"分层一致性"** - 根据变更类型选择不同的一致性级别:
- **关键变更**: 2PC 强一致(全员 commit 或 rollback)
- **重要变更**: Quorum 增强最终一致(多数派确认,允许脑裂)
- **普通变更**: Gossip 最终一致(10 秒内异步扩散)

> **📋 Gossip 参数说明**：Gossip 采用**分级收敛机制**，根据消息优先级使用不同的同步参数。
> 详见 `../00_overview/02_一致性级别定义.md` 中的 **Gossip 协议分级配置** 章节。

## 2. Gossip 协议设计

### 2.1 协议原理

**核心思想**: 病毒式扩散,每个节点定期随机选择其他节点同步元数据。

**收敛特性**:
- **对数收敛**: 节点数 N,收敛时间 O(log N)
- **容错性**: 容忍任意节点故障
- **最终一致**: 10 秒内所有节点达成一致

### 2.2 协议流程

```
┌─────────────────────────────────────────────────────────────┐
│                   Gossip 协议流程                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  节点 A                                              节点 B│
│    │                                                  │    │
│    │  1. 获取本地版本号                                 │    │
│    │  localVersion = 100                               │    │
│    │                                                  │    │
│    │  2. 随机选择节点 B                                 │    │
│    ├───────────────────────────────────────────────>│    │
│    │              VersionQuery(100)                   │    │
│    │                                                  │    │
│    │                         3. 返回本地版本号        │    │
│    │                                                  │<───┤
│    │              VersionResponse(95)                 │    │
│    │                                                  │    │
│    │  4. 本地版本更高,发送变更日志                      │    │
│    ├───────────────────────────────────────────────>│    │
│    │              ChangeLogs([96..100])               │    │
│    │                                                  │    │
│    │                         5. 应用变更日志          │    │
│    │                                                  │    │
│    │  6. 完成同步,更新版本号                           │    │
│    │  localVersion = 100                               │    │
│    │  remoteVersion = 100                              │    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 双向同步算法

```go
// GossipService Gossip 协议服务
type GossipService struct {
    interval  time.Duration    // 同步间隔 10s
    fanout    int              // 每轮随机节点数 2
    selector  NodeSelector     // 节点选择器
    store     MetadataStore    // 元数据存储
    transport Transport        // 网络传输
    stopCh    chan struct{}    // 停止信号
}

// 双向同步
func (g *GossipService) syncToNode(addr string) error {
    localVersion, _ := g.store.GetVersion()
    remoteVersion, err := g.transport.GetVersion(addr)

    // 本地更新,发送变更日志
    if localVersion > remoteVersion {
        logs := g.store.GetChangeLogs(remoteVersion)
        return g.transport.SendChangeLogs(addr, logs)
    }

    // 对方更新,请求变更日志
    if remoteVersion > localVersion {
        logs, err := g.transport.GetChangeLogs(addr, localVersion)
        if err != nil {
            return err
        }
        return g.store.ApplyChangeLogs(logs)
    }

    return nil
}

// Gossip 主循环
func (g *GossipService) Run() {
    ticker := time.NewTicker(g.interval)
    defer ticker.Stop()

    for {
        select {
        case <-ticker.C:
            // 随机选择 fanout 个节点
            peers := g.selector.SelectRandom(g.fanout)
            for _, peer := range peers {
                go g.syncToNode(peer)
            }
        case <-g.stopCh:
            return
        }
    }
}
```

## 3. Quorum 机制设计

### 3.1 协议原理

**核心思想**: 多数派确认,增强最终一致性。

**关键特性**:
- **多数派阈值**: N/2 + 1
- **并行发送**: 减少延迟
- **超时回滚**: 防止阻塞
- **允许脑裂**: 少数派可能独立提交

### 3.2 协议流程

```
┌─────────────────────────────────────────────────────────────┐
│                   Quorum 协议流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  发起节点                                              节点 B/C/D│
│    │                                                  │    │
│    │  1. 提议变更                                     │    │
│    │  ProposeChange(CreateShard)                     │    │
│    │                                                  │    │
│    │  2. 本地持久化                                   │    │
│    │  ApplyChange(change)                            │    │
│    │  version = 101                                  │    │
│    │                                                  │    │
│    │  3. 并行发送到所有节点                            │    │
│    ├────────────────────────────────────┐              │    │
│    │                                      │              │    │
│    ├────────────>│                         │<────────────┤    │
│    │              │  4. 应用变更            │              │    │
│    │              │  ApplyChange(change) │              │    │
│    │              │  version = 101        │              │    │
│    │              │                         │              │    │
│    │              │  5. 返回成功             │              │    │
│    │<─────────────┤                         ├────────────>│    │
│    │                                      │              │    │
│    │  6. 收集响应                                   │    │
│    │  successCount = 2 (包括自身)                │    │
│    │  threshold = 3 (N/2 + 1)                     │    │
│    │                                                  │    │
│    │  7. 达到多数派,确认提交                          │    │
│    │  ✅ Quorum Achieved!                           │    │
│    │                                                  │    │
│    │  8. 未达到多数派,超时回滚(如果发生)              │    │
│    │  ❌ Quorum Timeout, Rollback                   │    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 Quorum 实现

```go
// QuorumService Quorum 机制
type QuorumService struct {
    threshold int              // N/2 + 1
    timeout   time.Duration    // 30s
    store     MetadataStore    // 元数据存储
    transport Transport        // 网络传输
}

// ProposeChange 提议变更
func (q *QuorumService) ProposeChange(
    change *MetadataChange,
    nodes []string,
) error {
    // 1. 本地持久化
    if err := q.store.ApplyChange(change); err != nil {
        return err
    }

    // 2. 并行发送
    results := make(chan result, len(nodes))
    for _, node := range nodes {
        go func(addr string) {
            err := q.transport.SendChange(addr, change)
            results <- result{addr, err}
        }(node)
    }

    // 3. 等待多数派
    successCount := 1 // 自身已成功
    timeoutCh := time.After(q.timeout)

    for i := 0; i < len(nodes); i++ {
        select {
        case res := <-results:
            if res.err == nil {
                successCount++
                if successCount >= q.threshold {
                    return nil // 达到多数派
                }
            }
        case <-timeoutCh:
            if successCount >= q.threshold {
                return nil
            }
            // 未达标,回滚
            q.store.RollbackChange(change.Version)
            return ErrQuorumTimeout
        }
    }

    return nil
}

type result struct {
    addr string
    err  error
}
```

## 4. 无协调者简化版 2PC 协议设计

### 4.1 核心设计理念

**传统 2PC 的痛点**:
- 依赖独立协调者(性能瓶颈 + 单点故障)
- Prepare 阶段阻塞(资源锁定)
- 协调者故障(事务状态不一致)

**优化方案**:
- **发起节点兼任协调者**: 无需独立 TM
- **砍掉 Prepare 阶段**: 直接预提交,无资源锁定
- **Gossip 同步状态**: 异步扩散,最终一致

### 4.2 协议流程

```
┌─────────────────────────────────────────────────────────────┐
│               无协调者简化版 2PC 协议流程                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  阶段 1: 预提交(Pre-Commit)                                │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 1. 发起节点拆分事务,发送 Pre-Commit 指令            │   │
│  │ 2. 所有参与节点执行子事务,写入 WAL                   │   │
│  │ 3. 标记事务状态为「预提交」                           │   │
│  │ 4. 立即释放资源,向发起节点返回成功                   │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  阶段 2: 异步确认 + Gossip 状态同步                        │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 1. 发起节点收到所有响应,标记事务为「已提交」         │   │
│  │ 2. 发起 Gossip 协议,向参与节点扩散状态               │   │
│  │ 3. 参与节点接收状态,更新本地事务状态                 │   │
│  │ 4. 发起节点向客户端返回「事务成功」                  │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  阶段 3: 故障补偿                                         │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 1. 故障节点重启,读取本地事务状态表                   │   │
│  │ 2. 通过 Gossip 查询事务状态                          │   │
│  │ 3. 回放 WAL 日志,确认事务执行情况                    │   │
│  │ 4. 更新本地事务状态,完成自愈                         │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.4 预提交阶段实现

```go
// PreCommit 预提交阶段
func (c *TwoPhaseCommit) PreCommit(
    txID string,
    participants []string,
) error {
    c.phase = "precommit"
    c.votes = make(map[string]string)

    // 并行发送预提交指令
    for _, node := range participants {
        go func(n string) {
            err := c.transport.SendPreCommit(n, txID)
            if err == nil {
                c.votes[n] = "yes"
            } else {
                c.votes[n] = "no"
            }
        }(node)
    }

    // 等待所有响应
    timeoutCh := time.After(c.timeout)
    for len(c.votes) < len(participants) {
        select {
        case <-timeoutCh:
            return ErrTimeout
        default:
            time.Sleep(100 * time.Millisecond)
        }
    }

    return nil
}
```

### 4.5 决策阶段实现

```go
// Decide 决策阶段
func (c *TwoPhaseCommit) Decide(txID string) error {
    // 检查投票结果
    allYes := true
    for _, vote := range c.votes {
        if vote != "yes" {
            allYes = false
            break
        }
    }

    if allYes {
        c.decision = "commit"
    } else {
        c.decision = "rollback"
    }

    // 广播决策
    c.phase = "decide"
    c.BroadcastDecision(txID, c.decision)

    // Gossip 同步状态
    c.GossipState(txID, c.decision)

    return nil
}
```

### 4.6 Gossip 状态同步实现

```go
// GossipState Gossip 状态同步
func (c *TwoPhaseCommit) GossipState(txID, decision string) {
    // 构造状态消息
    stateMsg := &TransactionStateMessage{
        TXID:      txID,
        Decision:  decision,
        Timestamp: time.Now(),
    }

    // 异步扩散到所有节点
    for _, node := range c.participants {
        go func(addr string) {
            c.transport.SendTransactionState(addr, stateMsg)
        }(node)
    }
}
```

### 4.7 故障补偿实现

```go
// RecoverFromFailure 故障恢复
func (c *TwoPhaseCommit) RecoverFromFailure(txID string) error {
    // 1. 读取本地事务状态
    localState, err := c.store.GetTransactionState(txID)
    if err != nil {
        return err
    }

    // 2. 如果状态是「预提交」,查询最终状态
    if localState.Phase == "precommit" {
        // 通过 Gossip 查询其他节点
        finalState := c.queryTransactionStateViaGossip(txID)

        // 3. 应用最终状态
        if finalState.Decision == "commit" {
            // 回放 WAL 确认事务已执行
            c.replayAndCommit(txID)
        } else if finalState.Decision == "rollback" {
            // 回滚操作
            c.rollback(txID)
        }
    }

    return nil
}
```

## 5. 协议对比与选择

### 5.1 三种协议对比

| 维度 | Gossip | Quorum | 2PC |
|------|--------|--------|-----|
| **一致性级别** | 最终一致 | 增强最终一致(允许脑裂) | 强一致(全员 commit 或 rollback) |
| **收敛时间** | < 10 秒 | < 50ms | < 100ms |
| **网络开销** | 低(每轮 2 请求) | 中(并行 N 请求) | 高(组内全员交互) |
| **阻塞业务** | 否 | 是 | 是 |
| **适用场景** | 普通变更 | 重要变更 | 关键变更 |

### 5.2 一致性级别选择矩阵

| 业务场景 | 一致性要求 | 推荐协议 | 理由 |
|---------|-----------|---------|------|
| **分片创建** | 强一致 | 2PC | 全员 commit 或 rollback,避免数据不一致 |
| **主副本切换** | 强一致 | 2PC | 确保所有节点对主副本达成一致 |
| **节点加入/移除** | 强一致 | 2PC | 避免拓扑分裂 |
| **节点角色变更** | 增强最终一致 | Quorum | 多数派确认,容忍少数派不一致 |
| **分片副本调整** | 增强最终一致 | Quorum | 快速决策,容忍短暂不一致 |
| **节点状态更新** | 最终一致 | Gossip | 异步扩散,不阻塞业务 |
| **负载信息刷新** | 最终一致 | Gossip | 高频更新,最终一致即可 |

### 6.1 验证范围

|------|---------|---------|

### 6.2 关键不变式

**Gossip 协议**:
- **收敛性**: 所有节点最终达到一致状态
- **单调性**: 版本号单调递增

**Quorum 机制**:
- **多数派**: 只有达到多数派才能提交
- **原子性**: 提交或回滚,无中间状态

**2PC 协议**:
- **原子性**: 全员 commit 或全员 rollback
- **持久性**: 提交的事务不会丢失

---

## 7. 适用场景与局限性

### 7.1 适用场景

✅ **跨分片事务的最终一致性场景**:
- 电商订单的跨分片创建
- 用户数据的跨分片更新

✅ **单机-分布式一体的部署场景**:
- 需要在单机和分布式模式下无缝切换

✅ **高吞吐、低延迟的 KV 存储场景**:
- 对事务响应速度要求高
- 能接受最终一致性(除关键变更)

### 7.2 局限性

❌ **不支持全局强一致性事务**:
- 相比传统 2PC 的强一致性,优化版 2PC 是最终一致
- 存在短暂的状态不一致窗口

❌ **依赖 Gossip 的扩散速度**:
- 集群规模过大,Gossip 状态同步延迟可能增加

❌ **回滚成本较高**:
- 若某节点预提交失败,需要执行 WAL 回滚
- 回滚开销与子事务复杂度相关

## 8. Fencing Token 脑裂防护机制

> **新增于**: v1.1 (2026-02-14)

### 8.1 问题背景

**脑裂场景**：当网络分区发生时，可能出现多个节点同时认为自己拥有写入权限的情况：

```
时间线:
T1: Leader-A (Term=100) 正常写入
T2: 网络分区，Leader-A 与其他节点断开
T3: 其他节点选举 Leader-B (Term=99，因为未收到最新 Term)
T4: 网络恢复，Leader-B 尝试写入 ← 危险！
```

如果不加防护，Leader-B 的旧 Term 写入会覆盖 Leader-A 的新数据，导致数据损坏。

### 8.2 解决方案：Fencing Token

**核心思想**：每次写入必须携带单调递增的 Fencing Token（Term），旧 Token 的写入被拒绝。

```go
// FencingToken 防护令牌
type FencingToken struct {
    Term     uint64 // 任期号，单调递增
    LeaderID string // Leader 标识
}

// FencingStore 防护存储
type FencingStore struct {
    currentToken *FencingToken // 当前有效 Token
    termStorage  *TermStorage  // Term 持久化存储
    store        KVStore       // 底层存储
}

// Write 带防护的写入
func (s *FencingStore) Write(ctx context.Context, ns, key string, value interface{}, token FencingToken) error {
    s.mu.Lock()
    defer s.mu.Unlock()

    // 检查 Token 是否过期
    if s.currentToken != nil && token.Term <= s.currentToken.Term {
        return ErrStaleToken // 拒绝旧 Token 写入
    }

    // 执行写入
    if err := s.store.Put(ns, key, value); err != nil {
        return err
    }

    // 更新当前 Token
    s.currentToken = &token
    return nil
}
```

### 8.3 Term 持久化

**关键要求**：Term 必须持久化到磁盘，重启后不能回退。

```go
// TermStorage Term 持久化存储
type TermStorage struct {
    store KVStore // 底层持久化存储
}

// AdvanceTerm 推进 Term（只能递增）
func (t *TermStorage) AdvanceTerm(ctx context.Context) (uint64, error) {
    currentTerm, err := t.GetCurrentTerm(ctx)
    if err != nil {
        return 0, err
    }

    newTerm := currentTerm + 1
    if err := t.store.Put(NamespaceCluster, KeyCurrentTerm, newTerm); err != nil {
        return 0, err
    }

    return newTerm, nil
}
```

### 8.4 Leader 选举集成

```go
// LeaderManager Leader 选举管理器
type LeaderManager struct {
    nodeID      string
    termStorage *TermStorage
    currentTerm uint64
    isLeader    bool
}

// BecomeLeader 成为 Leader（推进 Term）
func (m *LeaderManager) BecomeLeader(ctx context.Context) (*FencingToken, error) {
    // 推进 Term
    newTerm, err := m.termStorage.AdvanceTerm(ctx)
    if err != nil {
        return nil, err
    }

    m.currentTerm = newTerm
    m.isLeader = true

    return &FencingToken{
        Term:     newTerm,
        LeaderID: m.nodeID,
    }, nil
}
```

### 8.5 防护流程

```
┌─────────────────────────────────────────────────────────────┐
│                   Fencing Token 防护流程                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  正常流程：                                                 │
│  1. Leader-A (Term=100) 写入成功                            │
│  2. currentToken = {Term: 100, LeaderID: "A"}               │
│                                                             │
│  脑裂场景：                                                 │
│  3. 网络分区，Leader-B 选举 (Term=99)                       │
│  4. Leader-B 尝试写入，携带 Token {Term: 99}                │
│  5. 检查：99 <= 100 → 拒绝写入                              │
│  6. 返回 ErrStaleToken                                      │
│                                                             │
│  正常切换：                                                 │
│  7. 新 Leader-C 选举，Term 推进到 101                       │
│  8. Leader-C 写入，携带 Token {Term: 101}                   │
│  9. 检查：101 > 100 → 允许写入                              │
│  10. currentToken = {Term: 101, LeaderID: "C"}              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 9. 2PC 超时机制

> **新增于**: v1.1 (2026-02-14)

### 9.1 问题背景

**传统 2PC 问题**：如果参与者无响应，协调者会无限期阻塞，导致资源锁定。

### 9.2 解决方案：带超时的 2PC

```go
// TwoPCMerkleCoordinator 带 Merkle Tree 的 2PC 协调器
type TwoPCMerkleCoordinator struct {
    defaultTimeout time.Duration
    // ...
}

// PreCommitWithTimeout 带超时的预提交
func (c *TwoPCMerkleCoordinator) PreCommitWithTimeout(
    ctx context.Context,
    tx *TwoPCTransaction,
    timeout time.Duration,
) error {
    // 创建带超时的上下文
    ctx, cancel := context.WithTimeout(ctx, timeout)
    defer cancel()

    // 创建 ACK 收集器
    ackCollector := NewAckCollector(len(tx.Participants))
    tx.SetAckCollector(ackCollector)

    // 执行预提交（异步）
    if err := c.PreCommit(ctx, tx); err != nil {
        return err
    }

    // 等待 ACK 响应（带超时）
    _, failedCount, success, err := ackCollector.WaitWithContext(ctx)
    if err != nil {
        // 超时，自动回滚
        c.Rollback(ctx, tx)
        return ErrPrepareTimeout
    }

    if !success {
        c.Rollback(ctx, tx)
        return fmt.Errorf("precommit failed: %d participants failed", failedCount)
    }

    return nil
}

// CommitWithTimeout 带超时的提交
func (c *TwoPCMerkleCoordinator) CommitWithTimeout(
    ctx context.Context,
    tx *TwoPCTransaction,
    timeout time.Duration,
) error {
    ctx, cancel := context.WithTimeout(ctx, timeout)
    defer cancel()

    return c.Commit(ctx, tx)
}
```

### 9.3 超时处理流程

```
┌─────────────────────────────────────────────────────────────┐
│                   2PC 超时处理流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  正常流程：                                                 │
│  1. 调用 PreCommitWithTimeout(tx, 5s)                      │
│  2. 发送 PreCommit 到所有参与者                             │
│  3. 等待 ACK 响应（最多 5s）                                │
│  4. 所有 ACK 到达 → 返回成功                                │
│                                                             │
│  超时流程：                                                 │
│  1. 调用 PreCommitWithTimeout(tx, 5s)                      │
│  2. 发送 PreCommit 到所有参与者                             │
│  3. 等待 ACK 响应...                                        │
│  4. 5s 超时，部分 ACK 未到达                                │
│  5. 自动执行 Rollback(tx)                                   │
│  6. 返回 ErrPrepareTimeout                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 9.4 错误定义

```go
var (
    ErrPrepareTimeout = errors.New("2PC PreCommit timeout")
    ErrCommitTimeout  = errors.New("2PC Commit timeout")
    ErrAckTimeout     = errors.New("2PC ACK wait timeout")
)
```

## 10. Gossip 事件驱动触发

> **新增于**: v1.1 (2026-02-14)

### 10.1 问题背景

**传统 Gossip 问题**：固定周期同步（如 10 秒），即使有变更也要等待下一个周期，导致同步延迟高。

### 10.2 解决方案：事件驱动 + 定时器双触发

```go
// EventDrivenGossipSync 事件驱动的 Gossip 同步
type EventDrivenGossipSync struct {
    eventChan         chan GossipEvent    // 事件通道
    ticker            *time.Ticker        // 定时器（兜底）
    pendingNamespaces map[string]bool     // 待同步的 Namespace
    // ...
}

// GossipEvent Gossip 事件
type GossipEvent struct {
    Type      GossipEventType // 事件类型
    Namespace string          // Namespace
    Key       string          // Key
    NodeID    string          // 节点 ID
    Timestamp time.Time       // 时间戳
}
```

### 10.3 触发机制

```
┌─────────────────────────────────────────────────────────────┐
│                Gossip 双触发机制                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  事件驱动触发（低延迟）：                                   │
│  1. 写入操作完成 → OnWrite(namespace, key)                  │
│  2. 事件发送到 eventChan                                    │
│  3. 事件处理循环立即接收                                    │
│  4. 触发 Gossip 同步                                        │
│  → 同步延迟：< 100ms                                        │
│                                                             │
│  定时器触发（兜底）：                                       │
│  1. 每 10 秒触发一次                                        │
│  2. 无论是否有变更都执行同步                                │
│  3. 保证最终一致性                                          │
│  → 同步延迟：≤ 10s                                          │
│                                                             │
│  批量优化：                                                 │
│  - 积累 5 个事件后批量触发                                  │
│  - 减少同步频率，提高效率                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 10.4 防风暴机制

```go
// OnWrite 写入事件触发（非阻塞）
func (s *EventDrivenGossipSync) OnWrite(namespace, key string) {
    event := GossipEvent{
        Type:      EventWrite,
        Namespace: namespace,
        Key:       key,
        Timestamp: time.Now(),
    }

    select {
    case s.eventChan <- event:
        // 成功发送
    default:
        // 通道满，丢弃事件（定时器会兜底）
        s.eventsDropped++
    }
}
```

**关键特性**：
- 非阻塞发送：通道满时丢弃事件
- 定时器兜底：保证最终一致性
- 批量优化：积累多个事件后批量同步

### 10.5 使用示例

```go
// 创建事件驱动 Gossip
config := &EventDrivenConfig{
    MerkleTree:    merkleTree,
    MetadataKV:    metadataKV,
    Transport:     transport,
    LocalNodeID:   "node-001",
    PeerSelector:  NewRandomPeerSelector(),
    EventChanSize: 1000,
    TickerDelay:   10 * time.Second,
}
sync := NewEventDrivenGossipSync(config)
defer sync.Close()

// 写入操作后触发

sync.OnWrite("meta:node:", "node-001")  // 立即触发 Gossip
```

## 11. 总结

### 8.1 核心价值

**"在分片级主从自治架构下,以最小的协议开销实现跨分片事务的一致性"**:
- 摒弃独立协调者,消除单点故障
- 砍掉 Prepare 阶段,降低阻塞开销
- Gossip 协议异步同步状态,适配高吞吐场景
- 完美契合单机-分布式一体的设计理念

### 8.2 设计原则

| 原则 | 说明 |
|------|------|
| **简单性** | 协议流程简单,易于理解和实现 |
| **性能优先** | 减少网络往返,降低延迟 |
