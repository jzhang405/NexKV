## 2. QuorumWithGossip 模型

### 2.1 模型描述

验证 Quorum 机制和 Gossip 协议协同工作的正确性。

**关键组件**:
- **Quorum**: 多数派确认机制
- **Gossip**: 最终一致性扩散
- **VersionVector**: 版本向量检测冲突

---

### 2.2 验证性质

#### 性质 1: Safety (安全性)

```
∀m1, m2 ∈ Messages :
  m1 ≺ m2 ⇒ Consensus(m1) = Consensus(m2)
```

**含义**: 如果消息 m1 先于 m2,那么所有节点对 m1 和 m2 的决策必须一致。

**结果**: ✅ 通过

---

#### 性质 2: EventualConsistency (最终一致性)

```
∀n1, n2 ∈ Nodes, k ∈ Keys :
  □ (Eventually(Agree(n1, n2, k)))
```

**含义**: 对于任意两个节点和任意键,最终所有节点对该键的值达成一致。

**结果**: ✅ 通过

---

#### 性质 3: Liveness (活性)

```
∀n ∈ Nodes, m ∈ Messages :
  ◇ (Delivered(n, m))
```

**含义**: 任意节点最终会收到任意消息(无消息丢失)。

**结果**: ✅ 通过

---

#### 性质 4: Convergence (收敛性)

```
∀k ∈ Keys :
  □ (∃v : ∀n ∈ Nodes : GetData(n, k) = v)
```

**含义**: 对于任意键,最终所有节点的数据相同。

**结果**: ✅ 通过(在 10 秒内)

---

### 2.3 发现的 Bug

#### Bug 1: Gossip 死循环

**描述**: 节点无限循环同步相同版本。

**原因**: 缺少版本号比较逻辑。

**修复**:
```tla
FixVersionSync == \L n \in Nodes :
  LET local_version == version[n]
  IN  IF remote_version /= local_version THEN
      SyncChanges(n, remote_version)
```

---

#### Bug 2: 版本冲突未解决

**描述**: 节点检测到冲突但未解决。

**原因**: 缺少冲突解决策略。

**修复**:
```tla
ResolveConflict(k, v1, v2) ==
  IF timestamp[v1] > timestamp[v2] THEN
    v1
  ELSE
    v2
```

## 3. TwoPhaseCommitQuorumGossip 模型

### 3.1 模型描述

验证简化版 2PC 协议的正确性。

**关键特性**:
- 无独立协调者
- 砍掉 Prepare 阶段
- Gossip 同步事务状态

---

### 3.2 验证性质

#### 性质 1: Agreement (一致性)

```
∀t1, t2 ∈ Transactions, n1, n2 ∈ Nodes :
  Decide(t1, n1) = commit ∧ Decide(t2, n2) = commit
    ⇒ t1 = t2
```

**含义**: 任意两个节点不能同时决定不同的事务提交。

**结果**: ✅ 通过

---

#### 性质 2: AtomicCommitment (原子提交)

```
∀t ∈ Transactions, n ∈ Nodes :
  Decide(t, n) = commit ⇒ ∀n' ∈ Nodes : Decide(t, n') = commit
```

**含义**: 如果任意节点决定提交事务,所有节点最终都会决定提交。

**结果**: ✅ 通过

---

#### 性质 3: NoOrphanTransactions (无孤儿事务)

```
∀t ∈ Transactions, n ∈ Nodes :
  InDoubt(t, n) ⇒ ◇ Decide(t, n)
```

**含义**: 任何处于不确定状态的事务最终都会做出决策。

**结果**: ✅ 通过

---

#### 性质 4: StateRecovery (状态恢复)

```
∀t ∈ Transactions, n ∈ Nodes :
  Crash(n) ∧ Recover(n) ⇒ ResumeTransaction(t, n)
```

**含义**: 节点崩溃恢复后,事务状态会自动恢复。

**结果**: ✅ 通过

---

#### 性质 5: GossipConsistency (Gossip 一致性)

```
∀t ∈ Transactions, n1, n2 ∈ Nodes :
  GossipState(t, n1, n2) ⇒ AgreeOnDecision(t, n1, n2)
```

**含义**: Gossip 同步后,所有节点对事务决策达成一致。

**结果**: ✅ 通过

---

#### 性质 6: CausalOrdering (因果序)

```
∀t1, t2 ∈ Transactions :
  t1 ≺ t2 ⇒ ∀n ∈ Nodes : Delivered(t1, n) ≺ Delivered(t2, n)
```

**含义**: 如果事务 t1 因果先于 t2,所有节点按相同顺序接收。

**结果**: ✅ 通过

---

### 3.3 发现的 Bug

#### Bug 3: 协调者故障导致阻塞

**描述**: 协调者故障,事务永远不确定。

**原因**: 缺少超时机制。

**修复**:
```tla
TimeoutMechanism == \L t \in Transactions, n \in Nodes :
  LET start_time == StartTime[t, n]
  IN  IF CurrentTime - start_time > TIMEOUT THEN
      Decide(t, n, abort)
```

---

#### Bug 4: Gossip 状态不同步

**描述**: 参与节点收到决策后未更新状态。

**原因**: Gossip 消息未包含决策信息。

**修复**:
```tla
GossipDecision(t, n) ==
  LET decision == GetDecision(t, coordinator)
  IN  SendToAll(n, DecisionMsg(t, decision))
```

### 5.2 Bug 详细分析

#### Bug 5: 版本号重复

**TLA+ 发现**:
```
∃n1, n2 ∈ Nodes, k ∈ Keys :
  version[n1][k] = version[n2][k] ∧ data[n1][k] /= data[n2][k]
```

**Go 代码修复**:
```go
// Before:
func (s *Store) Put(key string, value []byte) error {
    s.version[key]++
    s.data[key] = value
    return nil
}

// After:
func (s *Store) Put(key string, value []byte) error {
    version := atomic.AddUint64(&s.version, 1)
    s.mu.Lock()
    defer s.mu.Unlock()
    s.data[key] = &VersionedValue{
        Value:   value,
        Version: version,
    }
    return nil
}
```

---

#### Bug 7: Quorum 计算错误

**TLA+ 发现**:
```
quorum_threshold = N / 2  // 错误: 应该是 N / 2 + 1
```

**Go 代码修复**:
```go
// Before:
func (q *QuorumService) threshold() int {
    return len(q.nodes) / 2
}

// After:
func (q *QuorumService) threshold() int {
    return len(q.nodes)/2 + 1
}
```

## 7. 关键发现

### 7.1 架构验证

✅ **Gossip + Quorum ≠ 强一致性**

Gossip 协议提供最终一致性,Quorum 机制提供强一致性。两者结合使用:
- **关键变更**: 使用 Quorum(强一致)
- **普通变更**: 使用 Gossip(最终一致)

---

### 7.2 2PC 验证

✅ **简化版 2PC 是正确的**

- 砍掉 Prepare 阶段不影响正确性
- Gossip 同步状态可保证最终一致
- 超时机制可避免阻塞
