## 2. 角色职责

### 2.1 产品经理 (PM) - 🤖 AI Agent

#### 角色定位

> **核心职责**: 由 AI Agent 充当，负责需求分析、产品规划和项目协调，辅助架构师进行项目管理工作。

#### 主要职责

**需求管理**:
- 分析用户需求（从项目上下文提取）
- 编写和维护产品需求文档 (PRD)
- 需求优先级排序（基于技术可行性）
- 需求变更控制（与架构师确认）

**项目规划**:
- 制定项目里程碑（基于架构师的指导）
- 跟踪项目进度（自动化统计）
- 风险识别和上报（数据分析）
- 资源协调（协助架构师）

**文档产出**:
- 产品需求文档（PRD.md）
- 项目计划文档（project_plan.md）
- 需求评审纪要（requirement_review_minutes.md）
- 项目进度报告（project_init_report.md）

#### AI Agent 特性

**优势**:
- 24/7 可用，随时响应需求
- 快速生成文档和报告
- 数据驱动的分析能力
- 与开发流程无缝集成

**限制**:
- 需要架构师的指导和技术验证
- 缺乏真实用户反馈渠道
- 需要人工审核和修正

### 2.2 架构师 (Arch) - 👤 真实人员

#### 角色定位

> **核心职责**: 作为项目的**技术负责人**和**最终决策者**，负责整体技术架构、关键技术方案决策，以及把控项目的技术方向和质量标准。

#### 主要职责

**技术架构决策**:
- 设计系统整体架构（三层架构设计）
- 技术选型最终决策（sync.Map、TCP、MessagePack）
- 架构文档编写和评审（SAD、CPD、DDD）
- 技术路线图规划

**关键方案设计**:
- **一致性协议设计**: Gossip、Quorum、2PC 的方案决策
- **存储引擎设计**: MVStore + WAL 的架构决策
- **网络协议设计**: 自定义帧格式、编解码方案
- **集群管理设计**: 树形协调器、故障自愈机制

**代码审查与质量把控**:
- 核心代码的最终 Review（所有 PR 必须 Approve）
- 编码规范制定和执行（CDS.md）
- TLA+ 模型验证对接（确保实现与模型一致）
- 性能基准目标设定和验证

**AI Agent 协调**:
- 指导 AI Agent 的开发工作
- 评审 AI Agent 产出的代码和文档
- 解决 AI Agent 无法处理的复杂问题
- 技术难点攻关和指导

#### 独特价值

| 能力 | AI Agent | 真实架构师 |
|------|---------|-----------|
| **创造性决策** | ⚠️ 有限 | ✅ 核心 |
| **技术直觉** | ⚠️ 缺乏 | ✅ 关键 |
| **经验判断** | ⚠️ 基于数据 | ✅ 综合考量 |
| **责任承担** | ❌ 无法承担 | ✅ 最终负责 |
| **复杂问题解决** | ⚠️ 需要指导 | ✅ 独立解决 |

#### 关键产出

| 文档/决策 | 频率 | 说明 |
|----------|-----|------|
| **架构设计文档 (SAD)** | 项目初期 | 架构总览，必须由架构师主导 |
| **一致性协议设计 (CPD)** | 项目初期 | 协议设计，核心技术决策 |
| **技术方案决策** | 按需 | 关键技术决策记录 |
| **Code Review Approval** | 持续 | 所有核心 PR 必须 Approve |
| **TLA+ 模型对接** | 持续 | 确保实现与验证模型一致 |

#### 关键产出

| 文档 | 频率 | 用途 |
|------|-----|------|
| **架构设计文档 (SAD)** | 项目初期 | 架构总览 |
| **详细设计文档 (DDD)** | 按需 | 模块设计 |
| **技术方案文档** | 按需 | 技术决策记录 |

## 4. 协作机制

### 4.1 日常工作流

```
每日站会 (10:00, 15 分钟)
    ↓
任务执行
    ↓
Code Review (持续)
    ↓
CI/CD 自动测试 (持续)
    ↓
每日总结 (18:00)
```

---

### 4.2 Code Review 流程

#### Review 角色分工

| 文件/模块 | 作者 | Reviewer | Approver |
|----------|-----|----------|----------|
| **存储层代码** | 开发工程师 A | 开发工程师 B | 架构师 |
| **网络层代码** | 开发工程师 B | 开发工程师 A | 架构师 |
| **一致性协议代码** | 开发工程师 A | 开发工程师 B + 架构师 | 架构师 |
| **节点管理代码** | 开发工程师 B | 开发工程师 A + 架构师 | 架构师 |
| **测试代码** | 测试工程师 | 开发工程师 A/B | 架构师 |
| **部署脚本** | DevOps 工程师 | 开发工程师 A/B | 架构师 |

#### Review 标准

**必须项**:
- ✅ 代码格式化通过（gofmt）
- ✅ 静态检查通过（golangci-lint）
- ✅ 单元测试通过（go test）
- ✅ 代码注释完整
- ✅ 错误处理显式

**Review 要点**:
- 代码逻辑正确性
- 并发安全性
- 性能影响
- 错误处理
- 代码可读性
- 测试覆盖

### 4.3 技术评审流程

#### 评审类型

| 评审类型 | 触发条件 | 参与者 | 产出 |
|---------|---------|--------|------|
| **需求评审** | 新需求或需求变更 | PM + Arch + Dev | 需求评审纪要 |
| **设计评审** | 新模块或重大变更 | Arch + Dev | 设计评审纪要 |
| **代码评审** | PR 提交 | Dev + Arch | Review 意见 |
| **测试评审** | 测试计划完成 | QA + Dev | 测试评审纪要 |

```
    ↓

    ↓

    ↓

    ↓
Bug 关闭
```

```yaml
settings:
```

```yaml
name: CI/CD Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Go
        uses: actions/setup-go@v4
        with:
          go-version: '1.23'
      - name: Run tests
        run: |
          go test ./... -v
          go test ./... -race
          go test ./... -cover
```
