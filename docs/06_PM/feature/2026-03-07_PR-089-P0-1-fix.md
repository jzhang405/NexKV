## 🔍 Code Review 问题回顾

### P0-1: Lock/Unlock 死锁风险

**review 指出的问题**：

```go
// 原实现（有问题）
func (bl *BitmapLock) Lock(pageID uint64) {
    shard.mu.Lock()
    defer shard.mu.Unlock()

    for {
        readers := shard.readers[bit].Load()
        if readers == 0 {
            break
        }
        // ⚠️ 问题：频繁 Lock/Unlock 导致 CPU 空转
        shard.mu.Unlock()
        shard.mu.Lock()
    }
    // ...
}
```

**问题描述**：
1. ⚠️ **CPU 空转**（busy waiting）：while 循环不断 Lock/Unlock
2. ⚠️ **频繁锁操作**：在高并发下开销大
3. ⚠️ **性能下降**：读锁多时，写锁会一直空转

**review 结论**：虽然不是死锁（defer 保证 Unlock），但确实存在性能问题。

---

## ✅ 修复方案：sync.Cond

### 设计思路

使用 `sync.Cond` 的条件变量机制：
- `cond.Wait()`：阻塞等待，自动释放/获取锁，不占用 CPU
- `cond.Broadcast()`：唤醒所有等待的 goroutine

### 实现修改

#### 1. 结构体修改

```go
type lockShard struct {
    mu      sync.Mutex
    bitmap  atomic.Uint64
    readers [bitsPerWord]atomic.Uint32
    writer  atomic.Uint32

    cond    *sync.Cond  // ✅ 新增：条件变量
}
```

#### 2. 初始化修改

```go
func NewBitmapLock(shardCount int) *BitmapLock {
    bl := &BitmapLock{...}

    for i := range bl.shards {
        shard := &lockShard{}
        shard.cond = sync.NewCond(&shard.mu)  // ✅ 初始化
        bl.shards[i] = shard
    }

    return bl
}
```

#### 3. Lock 方法修改

```go
func (bl *BitmapLock) Lock(pageID uint64) {
    shard := bl.getShard(pageID)
    bit := bl.getBitInShard(pageID)

    shard.mu.Lock()
    defer shard.mu.Unlock()

    // ✅ 使用 cond.Wait() 替代忙等待
    for shard.readers[bit].Load() != 0 {
        shard.cond.Wait()  // 阻塞等待，不占用 CPU
    }

    shard.writer.Store(1)
    shard.bitmap.Store(shard.bitmap.Load() | (1 << bit))
}
```

#### 4. RLock 方法修改

```go
func (bl *BitmapLock) RLock(pageID uint64) {
    shard := bl.getShard(pageID)
    bit := bl.getBitInShard(pageID)

    shard.mu.Lock()
    defer shard.mu.Unlock()

    // ✅ 使用 cond.Wait() 替代忙等待
    for shard.writer.Load() != 0 {
        shard.cond.Wait()  // 阻塞等待，不占用 CPU
    }

    shard.readers[bit].Add(1)
    shard.bitmap.Store(shard.bitmap.Load() | (1 << bit))
}
```

#### 5. Unlock 方法修改

```go
func (bl *BitmapLock) Unlock(pageID uint64) {
    shard := bl.getShard(pageID)
    bit := bl.getBitInShard(pageID)

    shard.mu.Lock()
    defer shard.mu.Unlock()

    shard.writer.Store(0)
    shard.bitmap.Store(shard.bitmap.Load() &^ (1 << bit))

    // ✅ 唤醒等待的读锁
    shard.cond.Broadcast()
}
```

#### 6. RUnlock 方法修改

```go
func (bl *BitmapLock) RUnlock(pageID uint64) {
    shard := bl.getShard(pageID)
    bit := bl.getBitInShard(pageID)

    shard.mu.Lock()
    defer shard.mu.Unlock()

    newCount := shard.readers[bit].Add(^uint32(0))  // -1

    if newCount == 0 {
        shard.bitmap.Store(shard.bitmap.Load() &^ (1 << bit))
        // ✅ 唤醒等待的写锁
        shard.cond.Broadcast()
    }
}
```

## 🎯 其他 Code Review 问题

### P1-1: RLock 未释放 shard.mu ❌ **误报**

**review 声称**：
```
func (bl *BitmapLock) RLock(pageID uint64) {
    shard.mu.Lock()  // ⚠️ review 认为 defer 缺失
    // ...
}
```

**实际代码**：
```go
func (bl *BitmapLock) RLock(pageID uint64) {
    shard.mu.Lock()
    defer shard.mu.Unlock()  // ✅ 有 defer！
    // ...
}
```

**结论**: ✅ 代码正确，review 误报

---

### P1-2: readers 数组大小固定 ⚠️ **设计限制**

**当前设计**: `[bitsPerWord]atomic.Uint32` = 64 个

**限制**: 每个 shard 最多支持 64 个页面的独立锁

**扩展性**: 可通过增加 shard 数量扩展（最多 64 个分片）

**总容量**: 64 × 64 = 4096 个页面

**结论**: ⚠️ MVP 阶段可接受，后续可优化
