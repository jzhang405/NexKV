# WAL 文件、Snapshot 文件、Checkpoint 文件 设计方案（分布式 KV 存储专用）

> **文档类型**: 💡 技术建议（Proposals）
> **创建日期**: 2026-01-19
> **状态**: 📋 待讨论

在分布式 KV 存储系统中，**WAL（预写日志）、Snapshot（快照）、Checkpoint（检查点）** 三者是保障数据可靠性、提升崩溃恢复效率、控制存储开销的核心组件，三者各司其职又紧密协作，形成完整的数据持久化与恢复体系。下面从设计目标、核心格式、实现逻辑、协作流程四个维度，给出生产级落地设计方案。

---

## 一、 三者核心定位与设计目标（先明确分工）

### 1. WAL（Write-Ahead Log，预写日志）

**核心定位**：「实时保障」—— 所有数据更新操作（Put/Delete/Update）在写入存储引擎之前，先顺序写入 WAL 文件，是数据可靠性的最后一道防线。

**设计目标**：
1. 保证数据不丢失：节点崩溃后，通过回放 WAL 恢复未持久化到存储引擎的增量数据；
2. 高频写入高效：采用顺序写（磁盘顺序写吞吐量接近硬件上限），低CPU/IO开销；
3. 条目可校验、可回放：每个条目独立完整，支持崩溃后跳过损坏条目，继续回放有效数据。

**适用场景**：实时记录高频小批量数据更新，补充快照的增量数据。

### 2. Snapshot（快照）

**核心定位**：「全局镜像」—— 某一时刻整个节点（或分片）的全量数据/元数据的完整镜像，是数据恢复的基础。

**设计目标**：
1. 完整记录全局状态：包含某一时间点的所有有效数据，无需依赖其他文件即可独立恢复节点；
2. 压缩存储：采用高效压缩算法，减少磁盘占用；
3. 生成与加载高效：尽量减少对在线业务的影响，加载时快速恢复全量数据。

**适用场景**：节点初始化、崩溃后全量恢复、跨节点副本同步、数据归档。

### 3. Checkpoint（检查点）

**核心定位**：「关联桥梁」—— 记录「Snapshot 与 WAL 的关联关系」，以及一些辅助恢复的元信息，是提升恢复效率的关键。

**设计目标**：
1. 关联快照与 WAL：标记快照对应的 WAL 偏移量（即快照生成后，后续 WAL 条目从哪个位置开始有效）；
2. 简化恢复流程：恢复时直接通过 Checkpoint 找到最新快照和对应的 WAL 起始位置，无需遍历所有 WAL 文件；
3. 控制 WAL 体积：基于 Checkpoint 清理已归档到快照的老旧 WAL 文件，避免磁盘溢出。

**适用场景**：崩溃后快速定位恢复所需文件、WAL 文件生命周期管理、增量恢复优化。

### 三者核心协作关系

```
业务更新操作 → 写入 WAL（实时）→ 定期生成 Snapshot（全量镜像）→ 生成 Checkpoint（关联快照与 WAL）→ 基于 Checkpoint 清理老旧 WAL
↓
节点崩溃恢复 → 加载最新 Checkpoint → 基于 Checkpoint 加载最新 Snapshot（全量）→ 回放 Checkpoint 标记的 WAL 增量数据（快照之后的操作）→ 恢复到最新状态
```

## 二、 各文件详细设计（格式+实现）

### 1. WAL 文件设计（延续之前的条目级格式，生产级优化）

#### （1）文件整体结构

采用「滚动文件」模式，单个 WAL 文件大小限制（如 64MB/128MB），达到阈值后自动切换到新文件，文件命名格式：`wal-{timestamp}-{sequence}.bin`（例：`wal-1735689600-0001.bin`），便于排序和查找。

单个 WAL 文件内部结构（条目级链式存储）：

```
[条目1头（24B）][条目1数据（变长）][条目2头（24B）][条目2数据（变长）]...[末尾标记（8B）]
```

#### （2）核心字段定义（完善之前的格式）

##### ① 条目头（24B，固定长度，大端序）

| 字段         | 长度（字节） | 类型       | 说明                                                                 |
|--------------|--------------|------------|----------------------------------------------------------------------|
| Magic        | 4            | 字节数组   | 固定为 "NxWL"，验证条目有效性，防止解析非 WAL 数据                  |
| OpType       | 2            | uint16     | 操作类型（1=Put/2=Delete/3=Update），标记数据更新类型                |
| KeyLen       | 4            | uint32     | Key 二进制数据长度（最大 4GB，适配所有场景）                          |
| ValueLen     | 4            | uint32     | Value 二进制数据长度（Delete 操作时为 0）                            |
| OldValueLen  | 4            | uint32     | 旧 Value 长度（Update 操作时有效，用于回滚，其他操作为 0）           |
| TimestampLen | 2            | uint16     | 时间戳数据长度（固定为 8 字节，uint64 毫秒级时间戳，便于后续扩展）   |
| CRC32C       | 4            | uint32     | 条目数据（Key+Value+OldValue+Timestamp）的 CRC32C 校验值，验证完整性  |

##### ② 条目数据（变长，按顺序存储）

| 字段     | 长度来源                | 存储格式       | 说明                                                                 |
|----------|-------------------------|----------------|----------------------------------------------------------------------|
| Key      | 条目头的 KeyLen         | 二进制 []byte  | 业务 Key（字符串/哈希值等，经二进制转换/编解码后的原始字节流）        |
| Value    | 条目头的 ValueLen       | 二进制 []byte  | 业务 Value（结构化数据如 ClusterMetadata 经 MsgPack/Protobuf 编解码） |
| OldValue | 条目头的 OldValueLen    | 二进制 []byte  | 旧 Value（仅 Update 操作有效，用于恢复时回滚到更新前状态）            |
| Timestamp| 条目头的 TimestampLen   | 二进制 []byte  | uint64 毫秒级时间戳，记录操作发生时间，便于回溯和排序                |

##### ③ 末尾标记（8B，固定）

| 字段         | 长度（字节） | 类型       | 说明                                                                 |
|--------------|--------------|------------|----------------------------------------------------------------------|
| EOF Magic    | 8            | 字节数组   | 固定为 "NxWLEOF"，标记 WAL 文件写入完成（未写满的文件无此标记，视为不完整） |

#### （3）核心实现要点

1. **写入策略**：**先写 WAL，后写存储引擎/内存**，保证操作持久性；采用顺序写，避免随机 IO，提升写入吞吐量。
2. **刷盘策略**：支持「同步刷盘」（核心数据，如元数据更新）和「异步刷盘」（普通数据，如业务 KV 更新），通过配置控制，兼顾可靠性和性能。
3. **校验与容错**：回放时先验证 Magic 字段，再校验 CRC32C，校验失败则标记该条目损坏，跳过并记录日志，继续回放后续条目，不影响整体恢复。
4. **归档标记**：当生成 Checkpoint 时，在对应的 WAL 条目后添加「归档标记」，标记该条目已被快照包含，便于后续清理。

### 2. Snapshot 文件设计（全量镜像，高效压缩）

#### （1）文件命名与存储策略

- **命名格式**：`snapshot-{timestamp}-{version}.snap`（例：`snapshot-1735689600-0005.snap`），`version` 与 Checkpoint 版本一致，便于关联。
- **存储策略**：单个 Snapshot 为独立文件，生成后只读（不可修改），避免并发写入冲突；支持压缩存储（默认 ZSTD 轻压缩，兼顾压缩比和解压速度）。
- **清理策略**：保留最新 N 个 Snapshot（如 3 个），老旧 Snapshot 基于 Checkpoint 自动清理，避免磁盘占用过高。

#### （2）文件整体结构（分段式，便于加载与校验）

```
[文件头（64B）][元数据段（变长，压缩）][数据段（变长，压缩）][校验和段（32B）]
```

#### （3）核心字段定义

##### ① 文件头（64B，固定长度，大端序，便于快速解析）

| 字段         | 长度（字节） | 类型       | 说明                                                                 |
|--------------|--------------|------------|----------------------------------------------------------------------|
| Magic        | 4            | 字节数组   | 固定为 "NxSN"，验证快照文件有效性                                    |
| Version      | 4            | uint32     | 快照版本号，与 Checkpoint 版本一致，用于关联                          |
| Timestamp    | 8            | uint64     | 快照生成时间戳（毫秒级），标记快照对应的全局时间点                    |
| MetaLen      | 4            | uint32     | 压缩后的元数据段长度                                                  |
| RawMetaLen   | 4            | uint32     | 解压后的元数据段长度，用于校验解压是否完整                            |
| DataLen      | 4            | uint32     | 压缩后的数据段长度                                                    |
| RawDataLen   | 4            | uint32     | 解压后的数据段长度，用于校验解压是否完整                            |
| NodeID       | 16           | 字节数组   | 生成快照的节点 ID，分布式场景下标记快照归属                          |
| ShardID      | 8            | 字节数组   | 分片 ID（若为分片快照），全局快照则为全 0                            |
| CompressType | 2            | uint16     | 压缩算法类型（1=ZSTD/2=Snappy/3=LZ4），标记数据压缩方式              |
| Reserved     | 14           | 字节数组   | 预留字段，便于后续扩展，填充 0                                       |

##### ② 元数据段（变长，压缩存储）

**存储内容**：快照对应的全局元信息，包括：
1. 集群元数据（ClusterMetadata）：分片分布、节点状态、版本号等；
2. 快照生成时的 WAL 偏移量（对应 Checkpoint 的 WAL 起始位置）；
3. 存储引擎状态（如 RocksDB 的当前 SSTable 列表、Block Cache 配置）。

**存储格式**：结构化数据经 MsgPack/Protobuf 编解码为二进制，再通过文件头标记的压缩算法压缩后存储，减少磁盘占用。

##### ③ 数据段（变长，压缩存储）

**存储内容**：快照生成时刻的全量有效 KV 数据，按分片/Key 范围有序存储（便于快速加载和查找）。

**存储格式**：
1. 按 Key 哈希/范围分片存储，每个分片内部按 Key 有序排列；
2. 单个 KV 格式：`[KeyLen（4B）][Key（变长）][ValueLen（4B）][Value（变长）]`；
3. 整体经压缩算法压缩后存储，提升存储效率，减少加载时的磁盘 IO。

##### ④ 校验和段（32B，固定）

**存储内容**：文件头+元数据段+数据段的 SHA256 校验值（全局校验，确保快照文件完整无损坏）。

**作用**：加载快照时，先校验全局 SHA256，若不一致则标记快照损坏，切换到上一个可用快照。

#### （4）核心实现要点

1. **生成策略**：**后台异步生成**，避免阻塞在线业务；生成时先冻结内存数据（或加读锁），复制一份数据用于生成快照，复制完成后释放锁，不影响在线写入。
2. **增量生成优化**：不每次生成全量快照（开销大），可基于上一个快照生成增量快照，减少磁盘 IO 和生成时间（需在 Checkpoint 中标记快照类型）。
3. **加载策略**：**分段加载+内存映射（mmap）**，对于大快照文件，采用 mmap 映射到内存，避免一次性加载整个文件导致内存溢出，提升加载效率。
4. **兼容性**：快照版本号向前兼容，新版本节点可加载旧版本快照，便于集群升级。

### 3. Checkpoint 文件设计（关联桥梁，轻量可读）

#### （1）文件命名与存储策略

- **命名格式**：`checkpoint-latest.json`（最新检查点，覆盖式写入）、`checkpoint-{version}.json`（历史检查点，归档存储）。
- **存储策略**：采用 JSON 格式（轻量、可读、便于调试），单个文件体积极小（KB 级），无需压缩；最新检查点文件保持只读（生成后不修改），避免并发写入冲突。
- **核心作用**：作为「恢复入口」，节点启动时优先加载 `checkpoint-latest.json`，快速定位最新的快照和 WAL 文件。

#### （2）核心字段定义（JSON 格式，结构化存储）

```json
{
  "checkpoint_version": 5,          // 检查点版本号，与快照版本一致
  "node_id": "node-001",            // 节点 ID
  "shard_id": "shard-001",          // 分片 ID（全局节点为 "global"）
  "create_timestamp": 1735689600000,// 检查点生成时间戳（毫秒级）
  "snapshot_info": {                // 关联的最新快照信息
    "snapshot_file": "snapshot-1735689600-0005.snap",
    "snapshot_version": 5,
    "snapshot_size": 10485760,      // 快照文件大小（字节）
    "snapshot_checksum": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" // 快照 SHA256 校验值
  },
  "wal_info": {                     // 关联的 WAL 信息（快照之后的增量 WAL）
    "wal_start_file": "wal-1735689600-0001.bin", // 快照生成后的第一个 WAL 文件
    "wal_start_offset": 12345,      // 对应 WAL 文件中的起始偏移量（从该位置开始回放）
    "wal_latest_file": "wal-1735690200-0003.bin", // 最新的 WAL 文件
    "wal_latest_offset": 67890      // 最新 WAL 文件的当前偏移量
  },
  "cleanup_info": {                 // 清理信息，用于 WAL/快照归档
    "expire_wal_files": ["wal-1735688000-0001.bin", "wal-1735688600-0002.bin"],
    "expire_snapshot_files": ["snapshot-1735687200-0003.snap"]
  },
  "reserved": {}                    // 预留字段，便于后续扩展
}
```

#### （3）核心实现要点

1. **生成时机**：**与 Snapshot 一一对应**，每次生成快照后，立即生成对应的 Checkpoint 文件，先写入临时文件，再原子重命名为 `checkpoint-latest.json`，避免崩溃导致 Checkpoint 损坏。
2. **原子性保障**：生成 Checkpoint 时，先验证快照文件的完整性（校验 SHA256），再记录 WAL 偏移量，确保关联关系的准确性；采用原子重命名（`os.Rename`），避免部分写入。
3. **清理触发**：生成 Checkpoint 后，根据配置（如保留最新 3 个快照、保留最新 10 个 WAL 文件），自动清理 `cleanup_info` 中标记的过期文件，释放磁盘空间。
4. **容错机制**：若 `checkpoint-latest.json` 损坏，可遍历历史 Checkpoint 文件，选择最新的有效版本，避免无法恢复。

## 三、 三者协作流程（生产级核心流程）

### 1. 正常运行流程（数据写入+定期归档）

```
步骤1：业务发起 KV 更新操作（Put/Delete/Update）
步骤2：系统将操作转换为 WAL 条目，按格式写入当前 WAL 文件（顺序写，异步/同步刷盘）
步骤3：WAL 写入成功后，更新内存数据/存储引擎（RocksDB 等），返回业务操作成功
步骤4：定期触发快照生成（如每小时一次，或 WAL 文件累计达到 1GB 时）
       ① 后台协程冻结当前内存数据/存储引擎状态，获取最新 WAL 偏移量
       ② 生成全量/增量快照文件，压缩存储并计算 SHA256 校验值
       ③ 生成 Checkpoint 文件，关联快照文件和 WAL 偏移量，原子更新 checkpoint-latest.json
步骤5：Checkpoint 生成成功后，自动清理过期的快照和 WAL 文件，释放磁盘空间
步骤6：重复步骤1-5，持续处理业务操作，定期归档
```

### 2. 崩溃恢复流程（节点重启+数据恢复）

```
步骤1：节点重启，首先加载 checkpoint-latest.json，解析快照信息和 WAL 关联信息
步骤2：验证最新快照文件的完整性（校验 SHA256），若损坏则切换到上一个有效快照
步骤3：加载快照文件，解压并还原全量数据到内存/存储引擎，恢复到快照生成时刻的状态
步骤4：根据 Checkpoint 记录的 WAL 起始文件和偏移量，遍历后续所有有效 WAL 文件
步骤5：按顺序回放 WAL 条目（校验 Magic+CRC32C，跳过损坏条目），还原快照之后的所有增量操作
步骤6：回放完成后，更新内存数据/存储引擎状态，启动业务服务，对外提供访问
步骤7：生成新的 Checkpoint 文件，标记当前恢复后的状态，完成整个恢复流程
```

### 3. 副本同步流程（跨节点数据同步）

```
步骤1：新节点加入集群，向主节点请求最新的 Checkpoint 和快照文件
步骤2：主节点发送 checkpoint-latest.json 和对应的快照文件给新节点
步骤3：新节点加载快照文件，恢复全量数据
步骤4：主节点发送快照之后的所有 WAL 文件给新节点
步骤5：新节点回放 WAL 条目，同步增量数据，达到与主节点一致的状态
步骤6：新节点定期从主节点同步最新的 WAL 条目，保持数据一致性
```

## 四、 优化与落地注意事项

### 1. 性能优化

1. **WAL 批量写入**：缓存短时间内的小操作，批量写入 WAL 文件，减少磁盘 IO 次数，提升写入吞吐量。
2. **快照增量生成**：避免每次生成全量快照（开销大），基于上一个快照生成增量快照，仅存储变化的数据，减少生成时间和磁盘占用。
3. **Checkpoint 轻量化**：Checkpoint 仅存储关联信息，不存储实际数据，保证生成和加载的高效性。
4. **文件预分配**：生成 WAL/Snapshot 文件时，先预分配磁盘空间（`os.Truncate`），避免文件增长过程中的磁盘碎片，提升写入效率。

### 2. 可靠性保障

1. **多重校验**：WAL 条目级 CRC32C 校验、快照全局 SHA256 校验、Checkpoint 原子重命名，层层保障数据完整性。
2. **多副本存储**：核心的快照和 Checkpoint 文件可存储多副本（如节点本地+远程存储），避免本地磁盘损坏导致无法恢复。
3. **WAL 滚动保护**：保留至少一个未归档的 WAL 文件，避免 Checkpoint 生成失败导致数据丢失。
4. **恢复日志记录**：恢复过程中记录详细日志（如加载的快照版本、回放的 WAL 条目数、跳过的损坏条目数），便于问题排查。

### 3. 可运维性优化

1. **文件命名规范**：统一的命名格式，便于日志采集和人工排查（如按时间戳排序，快速找到最新文件）。
2. **监控指标暴露**：暴露快照生成成功率、WAL 写入吞吐量、Checkpoint 最新版本、磁盘占用率等指标，便于监控告警。
3. **手动干预接口**：提供手动生成快照、清理过期文件、切换 Checkpoint 版本的接口，便于运维人员手动处理异常。
4. **日志结构化**：采用 JSON 格式记录 WAL/快照/Checkpoint 的操作日志，便于 ELK 等工具采集和分析。

## 五、 与 PR-003 当前设计的对比

| 方面 | PR-003 当前设计 | 本方案建议 |
|------|----------------|-----------|
| **文件分离** | Checkpoint 文件包含完整数据（CheckpointData） | Checkpoint 仅包含元数据（指针类），Snapshot 为独立文件 |
| **Checkpoint 格式** | Protobuf 二进制（两段式：Header + Data） | JSON 可读格式（便于调试） |
| **Snapshot 格式** | 简单两段式（16B Header + Protobuf Data） | 分段式（64B Header + 压缩元数据 + 压缩数据 + SHA256） |
| **WAL 轮换** | 单文件 + Truncate（PR-004 实现） | 滚动文件（wal-{timestamp}-{seq}.bin） |
| **压缩** | 无压缩 | ZSTD/Snappy/LZ4 可选压缩 |
| **末尾标记** | 无 | WAL 文件 EOF Magic（"NxWLEOF"） |

**核心区别**：
- **PR-003**：Checkpoint = 元数据 + 完整数据（单文件方案）
- **本方案**：Checkpoint = 纯元数据（指针），Snapshot = 独立数据文件（双文件分离方案）

## 六、 总结

1. **分工明确**：WAL 保障实时数据不丢失，Snapshot 提供全量数据镜像，Checkpoint 关联两者并控制存储开销，三者协作形成完整的持久化体系。
2. **格式严谨**：WAL 采用条目级二进制格式，Snapshot 采用分段压缩格式，Checkpoint 采用轻量 JSON 格式，兼顾可靠性和效率。
3. **流程闭环**：正常运行时定期归档，崩溃后快速恢复，跨节点副本同步，满足分布式 KV 存储的核心需求。
4. **落地可行**：所有设计均基于生产级实践，无复杂依赖，可直接整合到现有分布式 KV 系统中，兼顾扩展性和容错性。
