| 分配次数 | 0 allocs/op | 0 allocs/op | 持平 |

#### 顺序测试
| 指标 | WithPool | WithoutPool | 差异 |
|------|----------|-------------|------|
| 延迟 | 19.32 ns/op | 0.5864 ns/op | **33x 更慢** ❌ |
| 内存 | 1 B/op | 0 B/op | 1 B 更差 |
| 分配次数 | 0 allocs/op | 0 allocs/op | 持平 |

**原因分析**:
- Page 结构过于简单（[4096]byte 数组）
- Go 编译器优化：栈上分配比堆上快
- sync.Pool 的 Get/Put 开销反而大于直接分配
- 零内存分配（都在栈上）

**结论**: ❌ **简单结构不适用 sync.Pool**

## 📈 性能对比总结

### 目标达成情况

| 目标 | 要求 | 实际结果 | 状态 |
|------|------|----------|------|
| pool 性能 | ≥ new 版本的 80% | Node: 14.9x ✅<br>Page: 0.11x ❌ | ⚠️ 部分达成 |
| 内存节省 | ≥ 50% | Node: 96.2% ✅<br>GC: 86.3% ✅ | ✅ 达成 |

### 关键发现

#### 1. ✅ sync.Pool 适用场景

**适用**（显著优势）:
- 复杂结构（动态切片、map）
- 高内存分配场景
- 高 GC 压力场景
- 长生命周期对象

**性能提升**:
- Node 并行: **14.9x** 延迟提升
- Node 内存: **96.2%** 节省
- GC 压力: **4.26x** 延迟提升 + **86.3%** 内存节省

#### 2. ❌ sync.Pool 不适用场景

**不适用**（性能下降）:
- 简单结构（固定大小数组）
- 栈上分配更快的场景
- 短生命周期小对象

**性能下降**:
- Page 并行: **9.17x** 更慢
- Page 顺序: **33x** 更慢

## 🎯 BTree 应用建议

### 应使用 sync.Pool 的组件

1. **Node 对象** ⭐ 高优先级
   - 原因: 动态切片，内存分配大
   - 预期收益: 14.9x 性能 + 96.2% 内存节省

2. **InternalPage/LeafPage 的 keys/values**
   - 原因: 动态增长，频繁分配
   - 预期收益: 类似 Node

3. **Path 复制路径**
   - 原因: 临时对象，高频创建销毁
   - 预期收益: 减轻 GC 压力

### 不应使用 sync.Pool 的组件

1. **Page.Data 字节数组** ❌
   - 原因: 固定大小，栈上分配更快
   - 数据: [4096]byte

2. **RootNode 根节点**
   - 原因: 长生命周期，不频繁创建
   - 保留: 直接分配

## 💡 优化建议

### 1. 选择性使用 sync.Pool

```go
// ✅ 推荐：Node 对象池
var nodePool = sync.Pool{
    New: func() any {
        return &Node{
            Keys:   make([][]byte, 0, MaxKeys),
            Values: make([][]byte, 0, MaxKeys),
        }
    },
}

// ❌ 不推荐：Page.Data 对象池
// Page.Data 是固定大小数组，栈上分配更快
```

### 2. 混合策略

- **复杂结构**: 使用 sync.Pool（Node, 内部切片）
- **简单结构**: 直接分配（Page.Data）
- **路径对象**: 使用 sync.Pool（临时对象）

### 3. 预分配容量

```go
// 预分配容量，减少扩容
node.Keys = make([][]byte, 0, 128)  // 预分配 128 个槽位
node.Values = make([][]byte, 0, 128)
```
