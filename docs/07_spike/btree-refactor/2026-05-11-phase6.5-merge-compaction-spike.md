## 一、概述

### 1.1 问题

BTree 当前有两个空间回收缺口：

| 缺口 | 现象 | 根因 |
|------|------|------|
| **删除后页面不合并** | 大量 key 被删除后，页面保持低利用率，树结构膨胀 | Phase 6.0 只有 Split 没有 Merge |
| **Tombstone 永久占位** | 逻辑删除的条目永远不清理，Page 有效容量持续下降 | 无后台 Compaction 机制 |

这两个问题本质上是同一个——**空间回收**——应在一次 PR 中统一解决。

### 1.2 当前状态

| 组件 | 状态 | 说明 |
|------|------|------|
| Merge/Borrow 接口 | Stub (6 个方法全部返回 `ErrNotImplemented`) | `storage.go:37-43` |
| `leafPageHandle.Delete()` | 物理删除已实现 | `leaf_page.go:165-190`，但 Delete 路径不使用它 |
| `PageHeader.TombstoneCount` | 缺失 | Phase 3 规范要求新增 |
| `PageHeader.deleteEpoch` | 缺失 | `constants.go:11` 注释暗示预留但 struct 无此字段 |
| Compaction 后台任务 | 无 | `SourceCompaction` / `ExecutionOrderCompaction` 已定义但未注册 |
| 页面下溢检测 | 无 | `Capacity()` 方法存在但无调用者 |
| `MergeThreshold = 0.5` | 已定义但未使用 | `constants.go:32` |

### 1.3 目标

在一次 PR 中实现**删除后的空间回收全链路**：

```
Delete(k) → Tombstone 标记 → 页面利用率下降
    → Lazy Merge: 低利用率页面与兄弟合并 → 树结构收缩
    → Compaction: 后台回收页面内 Tombstone 占用的 Entry 槽位
```

## 二、Lazy Merge 设计（Phase 6.5）

### 2.1 策略

**Lazy Merge**：删除后不立即合并，仅在后续写操作经过该页面时检查利用率，低于阈值才触发。

原因：
- 避免 Delete 热路径增加合并开销
- 合并可能级联传播到根，推迟到已有写操作的 CAS 重试循环中一并处理
- 与 B+Tree 经典实现（BoltDB/LMDB）的写时合并策略一致

### 2.2 触发条件

```
Delete 后页面利用率 = (Count - TombstoneCount) / Capacity < MergeThreshold (0.5)
```

触发合并的时机：
1. **Delete 路径**: 在 `writeOperation` 的 CAS 成功后检查。页面利用率低于阈值 → 标记 `NodeMerging` → 合并/借用 → 传播到父节点
2. **Split 时优化**: 如果页面已满但 Tombstone 比例 > 50%，优先 Compaction 而非 Split

### 2.3 合并算法

```
handleLeafMerge(leaf PageRef, path SearchPath):
  1. 通过父节点找到左/右兄弟
  2. 如果左兄弟存在且利用率 < MergeThreshold:
     MergeLeaves(left, leaf) → 新左叶子
     父节点 RemoveChild(leaf) + UpdateKey(left)
  3. 如果左兄弟利用率 ≥ BorrowThreshold (0.5):
     尝试 BorrowFromLeft — 左兄弟给一个 key
  4. 否则同上逻辑检查右兄弟
  5. 如果兄弟都不可合并/借用 → 不操作（留待下一次）
  6. 合并后父节点可能 underflow → 递归 handleInternalMerge
```

**关键约束**：
- 合并和借用都在 COW 语义下进行（分配新页面，CAS 替换引用）
- 使用 `NodeMerging` 状态标记（CAS 原子标记），防止并发合并（与 Split 的 `NodeSplitting` 对称）
- **双页 CAS 死锁预防**：合并涉及两个页面，必须按 **PageID 升序**依次 CAS 标记（lock ordering）。两个页面都标记成功后才继续；任一 CAS 失败则回滚已标记页面（恢复 `NodeNormal`），释放引用后从搜索路径重试。不引入 `NodeBorrowing` 独立状态（避免 5 种状态 × 2 页面的状态矩阵爆炸）
- 合并传播复用 Phase 6.0 的 path 数组索引机制

### 2.4 借用算法

当兄弟页面利用率较高（≥ 0.5）时，借一个 key 而非合并整页：

**Leaf Borrow**：
```
BorrowFromLeft(self, sibling):
  1. 取 sibling 的最大 key → 插入 self 的最小位置
  2. sibling 物理删除该 key（COW 重建）
  3. 父节点更新 separator key（self 的新最小 key）

BorrowFromRight(self, sibling):
  1. 取 sibling 的最小 key → 插入 self 的最大位置
  2. sibling 物理删除该 key
  3. 父节点更新 separator key（sibling 的原最小 key → 新最小 key）
```

**Node Borrow**（内部节点版本）：
```
BorrowFromLeftNode(self, sibling, separator):
  1. sibling 的最后一个 child + 对应的 separator key → 插入 self 的头部
  2. sibling RemoveChild(lastIdx)
  3. 父节点更新 separator

BorrowFromRightNode: 对称操作
```

### 2.5 mergeRoot

当根节点只有一个子节点时，降低树高度：

```
mergeRoot():
  if root.ChildCount() == 1:
      childID := root.GetChild(0)
      childPI := storage.GetPageInfo(childID)           // 构造 *PageInfo
      rootRef.ReplaceRoot(oldRootPI, childPI, nil)      // 原子替换，新 root 是叶子时 children cache = nil
      // 旧 root PageInfo 失去引用，Go GC 回收
```
> **注意**：`ReplaceRoot` 而非裸 `CAS`，因为 `rootRef.CAS` 接受 `*PageInfo` 而非 `PageID`。
> 新 root 为叶子时 `children` cache 为 nil，reader 通过 `pInfo.IsLeaf` 判断不走 children cache 路径（H2 决议）。

### 2.7 Merge/Borrow 接口定义（遵循 ISP）

将 Merge/Borrow 6 方法从 `BTreeStorage` 胖接口中提取为独立接口 `PageMerger`：

```go
// btree/page_merger.go — 接口定义（btree 层）
type PageMerger interface {
    // Leaves
    MergeLeaves(left, right LeafPage) (LeafPage, error)
    BorrowFromLeftLeaf(self, sibling LeafPage) (LeafPage, LeafPage, error)
    BorrowFromRightLeaf(self, sibling LeafPage) (LeafPage, LeafPage, error)

    // Internal Nodes
    MergeNodes(left, right NodePage, separator []byte) (NodePage, error)
    BorrowFromLeftNode(self, sibling NodePage, separator []byte) (NodePage, NodePage, []byte, error)
    BorrowFromRightNode(self, sibling NodePage, separator []byte) (NodePage, NodePage, []byte, error)
}
```

## 三、Compaction 设计（Tombstone Phase 3）

### 3.1 策略

后台周期性扫描 + 按需触发，物理回收页面内 Tombstone 占用的 Entry 槽位。

```
Compaction 触发条件（满足任一）：
  1. Page.TombstoneCount / Page.Count > CompactionThreshold (默认 0.5)
  2. 定时器触发（默认 30s）
  3. Split 前检查 — 高 Tombstone 页优先 Compaction 而非 Split
```

### 3.2 Compaction 流程

```
CompactPage(pageRef):
  1. 获取 PageHandle → 统计 TombstoneCount
  2. 如果 TombstoneCount == 0 → 跳过
  3. COW 分配新页面
  4. 遍历页面所有 Entry：
     - 解析 MVCC Flag
     - 非 Tombstone → 写入新页面
     - Tombstone → 跳过
  5. CAS 替换 pageRef.pInfo → 指向新页面
  6. 旧页面 Release → Go GC 回收
```

**并发安全**：
- Compaction 使用 CAS 乐观锁（与 Split 相同模式）
- 如果 `NodeSplitting` 或 `NodeMerging` 标记存在 → 跳过本周期
- Compaction 不修改 key 的内容，只移除 Tombstone entry，不影响 VersionChain

**GC 安全性**：
- Phase 3 GC 的 `reclaimed` 标记只作用于 VersionChain 节点，不影响 BTree 页面
- Compaction 物理移除 Tombstone 时，所有活跃事务的 snapshotTS 必然 > Tombstone 的 commitTS（因为 GC Watermark 保证）
- Compaction 在 GC Prune 之后执行，确保没有活跃事务需要该 Tombstone

### 3.3 PageHeader 扩展

```go
// offheap/page_layout.go — PageHeader 扩展
type PageHeader struct {
    version        uint64 // 8 bytes
    prevPage       uint32 // 4 bytes
    nextPage       uint32 // 4 bytes
    extraChild     uint64 // 8 bytes
    count          uint16 // 2 bytes
    pageType       uint8  // 1 byte
    deleted        uint8  // 1 byte — page-level deletion marker
    tombstoneCount uint16 // 2 bytes — Phase 6.5: per-entry tombstone counter
    deleteEpoch    uint64 // 8 bytes — Phase 6.5: epoch when safe to physically reclaim
}
// New SizeofPageHeader = 56 bytes (matches constants.go HeaderSize)
```

**字段语义**：
- `tombstoneCount`：页面内 Tombstone 条目数量。Insert/Update 后维护（Set Tombstone → +1，Update 覆盖 Tombstone → -1，物理 Delete → -1）
- `deleteEpoch`：最后一个 Tombstone 被物理回收的 epoch。Compaction 后递增。**当前 Phase 6.5 暂不启用**（单节点无需 epoch 保护），字段预留。

> **C3/C5 冲突最终决策**（二轮评审 2026-05-13）：
> `tombstoneCount` **保留在 `PageHeader` 中**（offheap 层），不走 side-map 方案。
> **理由**：COW 路径依赖 `copyPage()` 全页 memcpy 自动携带 tombstoneCount 以保证原子性（C3 硬需求）；若改用 `map[PageID]uint16`，每次 COW 复制都需要额外加锁读 map，性能劣化且引入新的并发复杂度。这是 offheap 层承载少量 btree 语义的**例外**，在 `page_layout.go` 的 `tombstoneCount` 字段处加注释 "write-path metadata, maintained under COW atomicity guarantee"。
> `deleteEpoch` 保持预留（Phase 4+ 启用），当前不参与任何逻辑路径。

### 3.4 TombstoneCount 维护

```
Insert(key, value):          tombstoneCount 不变（新条目非 Tombstone）
Update(key, oldTombstone):   tombstoneCount -= 1（Tombstone 被覆盖）
Delete(key):                 tombstoneCount += 1（Set Tombstone Flag）
物理 Delete(idx):            tombstoneCount -= 1（移除 Tombstone 条目）
Compaction 重建页面:         tombstoneCount = 0（所有 Tombstone 已清除）
```

### 3.5 后台 Compaction 任务

**架构分层**（遵循 DIP/ISP）：
- **application 层**：定义 `CompactionTask` + 注册到 `TaskScheduler`
- **btree 层**：仅暴露 `Compact(wp WatermarkProvider)` 方法，不持有 scheduler/task 引用
- 依赖方向：`application → concurrency.TaskScheduler`，`application → btree.Compact()`

```go
// internal/application/compaction/task.go — application 层
const TaskNameCompaction = "btree-compaction"

type CompactionConfig struct {
    Interval  time.Duration // 默认 30s
    Threshold float64       // 默认 0.5 (TombstoneCount/Count)
}

type CompactionTask struct {
    bt     *btree.BTree
    wp     btree.WatermarkProvider
    config *CompactionConfig
}

// 在 application 组装层注册到 TaskScheduler
scheduler.RegisterTask(
    name:           TaskNameCompaction,
    priority:       TaskPriorityIdle,        // 最低优先级
    executionOrder: ExecutionOrderCompaction, // = 3
    executeFunc:    task.run,
)
```

**Compaction 周期**：

```go
func (t *CompactionTask) run() {
    // 1. 遍历所有页面：利用 BTree 叶子链 nextPage 指针顺序扫描
    //    从最左叶子开始，每次通过 PageRef → PageInfo.nextPage 跳转
    //    (PageHeader.prevPage/nextPage 已构成双向链表，无需 DFS 遍历树结构)
    // 2. 对每个页面：如果 TombstoneCount/Count > config.Threshold → btree.CompactPage
    // 3. 内部逐条验证 entry.commitTS < wp.Watermark() 后再物理移除
    // 4. 更新 metrics
}
```

> **遍历策略**：利用 `PageHeader.prevPage/nextPage` 构成的叶子链顺序扫描，无需 DFS 递归遍历内部节点。仅扫描叶子页（Tombstone 只存在于叶子层），内部节点不参与 Compaction。遍历期间持有 `PageRef` 防止页面被释放。

### 3.6 与 GC 的协作顺序

**最终决策（二轮评审）**：采用 **WatermarkProvider 接口**，Compaction 内部校验 `commitTS < watermark` 后再物理移除 Tombstone。不采用 "GC Cycle 最后一步调用 compactCycle"（耦合模块生命周期）。

```go
// btree/compaction.go — Compaction 依赖的轻量契约
type WatermarkProvider interface {
    Watermark() hlc.Timestamp
}
```

编排在 application 层通过纯函数完成（不引入 `SpaceRecyclingOrchestrator` 接口——Phase 6.5 scope 下函数调用足够，符合 YAGNI）：

```
GC Cycle:
  1. ActiveTxRegistry.Watermark() → 计算安全水位
  2. VersionChain.Prune(watermark) → 标记 reclaimed
  3. Prepend 时清理链头 reclaimed 节点

Compaction Cycle（由 application 层编排在 GC 之后调用）:
  1. btree.Compact(watermarkProvider) → 扫描活跃页面
  2. 对高 Tombstone 页面：验证 entry.commitTS < watermark → CompactPage
  3. TombstoneCount 归零
```

## 六、风险与约束

| 风险 | 缓解 |
|------|------|
| Merge 传播 CAS 冲突（多个线程删除相邻 key） | `NodeMerging` 状态标记 + CAS 重试（与 Split 相同模式） |
| Compaction 与 Merge 的竞争（同一页面同时触发两者） | Compaction 优先级最低，遇到 `NodeMerging`/`NodeSplitting` 跳过 |
| TombstoneCount 维护遗漏 | 集中在 `leaf_page.go` 的 COW 方法中维护，单点更新 |
| Compaction 误删可见 Tombstone | 在 GC Prune 之后执行（Watermark 保证安全）|
| PageHeader 扩展破坏兼容性 | `constants.go` 中 `HeaderSize=56` 已预留空间，offheap 页面格式不变 |
| MergeRoot 降低树高度时并发读 | `replaceRoot` 使用 CAS，旧 root 子树 COW 保护不回收 |

### Out of Scope

| 事项 | 原因 |
|------|------|
| `deleteEpoch` 实际使用 | 单节点无需 epoch，字段预留至 Phase 4 |
| 分布式 Merge 协调 | 同 Phase 3 WAL+GC，单节点 scope |
| Compaction 采样/增量策略 | 初期全量遍历，后续按需优化 |
| BTree 分片 Compaction | Phase 4 分布式 BTree |

### 7.1 CRITICAL（6 条）

| # | 来源 | 问题 | 决议 |
|---|------|------|------|
| C1 | 存储引擎 | **Merge 在 writeOperation 中的生命周期定位缺失**。CAS 成功后 `path.ReleaseAll()` 已释放搜索路径，Merge 传播无法定位父/兄弟节点。需明确 Merge 检查点的精确位置（在 CAS 成功后、path 释放前）。 | 在 `writeOperation` success 分支中，CAS 成功后立即检查 `IsSparse`，此时 path 未释放。 |
| C2 | Go 并发 | **`NodeMerging` 只标记稀疏页不标记兄弟页**。Merge 涉及**两个页面**但 CAS 标记只保护一侧，兄弟页可能被并发 Split/Borrow。 | 对两个页面都做 `NodeMerging` CAS 标记。**按 PageID 升序加锁**（lock ordering）防止死锁：线程 A 合并 (P1,P2) 和线程 B 合并 (P2,P1) 不会相互等待。两个页面都标记成功后才继续；任一失败回滚已标记页面，释放引用后重试。不引入 `NodeBorrowing` 独立状态（状态爆炸）。参见 §2.3 关键约束。 |
| C3 | Go 并发 | **TombstoneCount 维护点错位**。`leafPageHandle.Insert/Update/Delete` 在字节级别操作，不解析 MVCC Flag，无法在 COW 原子路径中同步维护 tombstoneCount。当前 mutateFunc 只返回 `newPageID` 和 `delta`，无法传递 tombstoneCount 调整量。 | 在 COW 副本上设置 tombstoneCount：`leafPageHandle` 新增 `SetTombstoneCount(n uint16)` 方法。`copyPage()` memcpy 自动携带旧 tombstoneCount，mutateFunc 在该值基础上做增量调整（+1 Tombstone、-1 覆盖、-1 物理删除）。mutateFunc 返回签名扩展为 `(newPageID uint32, countDelta int16, tombstoneDelta int16)`。参见 §3.3 C3/C5 最终决策。 |
| C4 | Go 并发 | **Merge 传播的 parent CAS 竞争**。`RemoveChild` + `InsertChild` 并发无保护，`handleParentCASWithSpin` 只处理 InsertChild 场景，完全不适用于 RemoveChild。 | **最终决策**：采用 **versioned child list** 方案。NodePage header 新增 `childVersion uint32`，每次 child 变更（InsertChild/RemoveChild）递增。CAS 条件包含 `expectedChildVersion`。粒度细于 parent `NodeMerging` 标记（后者阻止该 parent 下所有 child 的并发 Split，降低写入吞吐）。Split 的 `InsertChild` 已可通过 count 变化校验，Merge 的 `RemoveChild` 使用 `childVersion` 显式保护。 |
| C5 | DDD | **`PageHeader` 分层污染**。`tombstoneCount` 和 `deleteEpoch` 是 btree/MVCC 领域概念，不应写入通用 mmap 页面管理层 `offheap/page_layout.go`。 | **最终决策（二轮）**：`tombstoneCount` 保留在 `PageHeader`，作为 COW 原子性要求的例外。`copyPage()` memcpy 自动携带它，避免 side-map 方案的锁竞争。在字段注释中标注 "write-path metadata, maintained under COW atomicity guarantee"。`deleteEpoch` 预留但不在 Phase 6.5 使用。参见 §3.3 C3/C5 冲突决策。 |
| C6 | DDD | **`BTreeStorage` 接口膨胀**。15 个方法含 6 个 Merge/Borrow stub，承载了页面生命周期 + 结构性重组两大职责，违反 ISP。 | 将 Merge/Borrow 提取为独立接口 `PageMerger`，`OffheapBTreeStorage` 通过组合实现。`handleLeafMerge` 接收 `PageMerger` 而非 `BTreeStorage`。 |

### 7.2 HIGH（8 条）

| # | 来源 | 问题 | 决议 |
|---|------|------|------|
| H1 | 存储引擎 | Merge 三节点 CAS 顺序未定义（父节点 CAS vs 兄弟 CAS vs 叶子 CAS）。如果先 CAS 父节点成功后兄弟 CAS 失败，系统进入不一致状态。 | 父节点 CAS 为 Merge 的"提交点"：**先 CAS 父节点（RemoveChild + UpdateKey），成功后叶子+兄弟标记为 Redirect**。父节点 CAS 失败 → 已分配 COW 页面 Free → 重试。 |
| H2 | 存储引擎 | `mergeRoot` CAS 签名不匹配。`rootRef.CAS(old, new *PageInfo)` 要求 `*PageInfo`，但 `GetChild(0)` 返回 `PageID`。且新 root 是叶子时 children cache 应为 nil，与 `ReplaceRoot` 假设冲突。 | 正确实现：构造 leaf 类型 `*PageInfo`，调用 `rootRef.ReplaceRoot(oldRootInfo, newLeafInfo, nil)`。验证 reader 在 `pInfo.IsLeaf=true` 时不走 children cache 路径。 |
| H3 | 存储引擎 | Compaction 与 GC 执行顺序无强制保障。两者是独立后台循环，不存在天然的先后顺序。若 Compaction 先于 GC，Tombstone 被物理移除时活跃事务仍可能需要它。 | **最终决策**：采用 `WatermarkProvider` 接口（单方法 `Watermark() hlc.Timestamp`），Compaction 内部逐条验证 `commitTS < watermark` 后再物理移除。编排在 application 层以纯函数 `runRecyclingCycle(gc, btree, watermarkProvider)` 完成。参见 §3.6。 |
| H4 | Go 并发 | Merge 传播路径缺少 `toFree`/`toRelease` 模式。Split 路径通过 `toFree` 和 `toRelease` 切片追踪 COW 页面，Merge 未定义类似机制，sibling COW 页面可能泄漏。 | 借鉴 `handleInternalSplit` 的清理模式，Merge 函数中声明 `toFree`/`toRelease`，defer 在非成功路径上统一清理。 |
| H5 | Go 并发 | Merge + Split 同时修改 parent 时的活锁风险。两者都想 CAS grandparent（RemoveChild vs InsertChild），持续失败形成活锁。 | **最终决策**：采用**指数退避 + 随机抖动 + 确定性优先级**。优先级：Split > Merge > Compaction（避免上溢比回收空间更紧急）。Merge 检测到 CAS 冲突时退让 `random(1ms, 5ms)`，给 Split 完成窗口。使用 `childVersion` 检测冲突（与 C4 统一），而非额外的 parent 状态标记。双重退避（double backoff）由确定性优先级消除。 |
| H6 | DDD | GC → Compaction 协作缺乏显式领域契约。当前仅文档注释约定顺序，未通过类型系统强制执行。 | **最终决策**：采用 `WatermarkProvider` 接口（编译期契约），但不引入 `SpaceRecyclingOrchestrator` 编排接口。Phase 6.5 单节点 scope 下，application 层纯函数 `func runRecyclingCycle(gc *GC, bt *BTree, wp WatermarkProvider)` 足够。`Orchestrator` 接口留到 Phase 4 分布式阶段按需引入（YAGNI）。 |
| H7 | DDD | CompactionTask 注册位置未定。若在 BTree 内部注册会引入 `BTree → concurrency.TaskScheduler` 反向依赖。 | **最终决策**：`CompactionTask` 完全在 application 层定义——包括 struct、周期配置、调度器注册。BTree **仅暴露 `Compact(wp WatermarkProvider)` 方法**，不持有任何 scheduler/task 引用。依赖方向：`application → concurrency.TaskScheduler`，`application → btree.Compact()`。Step 4 伪代码中的 btree 包内 `CompactionTask` 需修正。 |
| H8 | DDD | `IsSparse(threshold)` 模糊了接口职责边界。`threshold` 参数暗示调用者知道阈值策略，且若未来叶子/内部节点阈值不同则需改签名。 | 实现为独立辅助函数 `isLeafSparse(leaf, threshold) bool` 而非接口方法。或定义轻量 `SparseChecker` 接口。 |

### 7.3 MEDIUM（9 条）

| # | 来源 | 问题 | 决议 |
|---|------|------|------|
| M1 | 存储引擎 | `NodeMerging` 与 `NodeSplitting` 互斥关系未说明。同一页面同时满足 Split 和 Merge 条件时优先级未定义。 | **优先级**：Split > Merge > Compaction。避免上溢最紧急；Merge 可延迟；Compaction 是纯优化。Compaction 在 Split 前检查高 Tombstone 比例（>50%）→ 优先 Compaction 而非 Split 是例外。Compaction 不单独引入 `NodeCompacting` 状态，通过 `NodeNormal` + CAS 保护。 |
| M2 | 存储引擎 | `NodePage.RemoveChild` 实现尚为 stub，其 COW 语义需精确定义（separator 的调整逻辑）。 | 补充 RemoveChild 的完整 COW 算法描述。特别注意 `count==1` 时 `extraChild` 的处理。 |
| M3 | 存储引擎 | Merge 未考虑 Tombstone 对合并后利用率的影响。两个高 Tombstone 比例页合并后仍需立即 Compaction。 | MergeLeaves 在 COW 构建新页面时可顺便跳过 Tombstone（Merge+Compaction 合并为一次操作）。标注为优化项。 |
| M4 | 存储引擎 | Borrow 的 separator key 更新语义未精确定义。父节点需要 `UpdateSeparator`，不同于 Split 的 `InsertChild` 模式。 | 需要专门的 `updateSeparatorInParent` 函数（Reuse `ReplaceChild` 模式）。ChildrenCache separator 也需同步更新。 |
| M5 | 存储引擎 | COW memcpy 使 TombstoneCount 随全页字节复制。但 `InitLeafPage` + 逐条 `InsertLeafEntry` 的 rebuild 路径需要先 `SetTombstoneCount(0)` 再手动计算。 | 统一 COW 路径使用 `copyPage` 模式（memcpy 4096B），避免分段初始化。Rebuild 场景另处理。 |
| M6 | Go 并发 | Compaction 的 TOCTOU 窗口：检查 `NodeMerging/NodeSplitting` 后到 CAS 前状态可能变化，导致无用的 COW 页面分配。 | Compaction CAS 循环内加入 `if pInfo.NodeState != NodeNormal { break }` 快速退出，避免分配后才发现状态改变。 |
| M7 | Go 并发 | Lazy Merge 检查在 write 热路径上增加延迟（CAS 成功后加载新页面 + 计算利用率 + 可能触发传播）。 | 将 Merge 触发改为异步：CAS 成功后仅记录事件到 channel，异步 goroutine 执行实际 Merge。或文档显式标注此 trade-off。 |
| M8 | DDD | `NodeMerging` 状态引入隐式耦合——Compaction 和 WriteOperation 都需知道所有可能的状态枚举值。 | 定义 `PageInfo.IsBusy() bool` 方法封装状态检查逻辑（返回 `state != NodeNormal && state != NodeRoot`）。新增状态时只需修改一处。在 Phase 6.5 中随 `NodeMerging` 引入同步实现（`page_info.go`）。 |
| M9 | DDD | `CompactionConfig` 定义层面与 `GCConfig` 不一致。两者都是后台回收配置却分处不同包。 | 保持 `CompactionConfig` 在 btree 包，但接口风格与 `GCConfig` 统一（Interval + Threshold 字段模式）。 |

### 7.4 LOW（7 条）

| # | 来源 | 问题 | 决议 |
|---|------|------|------|
| L1 | 存储引擎 | MergeThreshold 和 BorrowThreshold 都设为 0.5，Borrow 只在 sibling 利用率刚好 ≥0.5 时触发。 | 保持 0.5/0.5（互补覆盖无 gap），在注释中说明选择理由。预留 `BorrowThreshold` 独立常量供后续调优。 |
| L2 | 存储引擎 | Merge 失败路径中 orphan COW 页面回收应复用 Split 的 `toFree`/`toRelease` 模式。 | 实施时与 Split 的 cleanup 机制统一。 |
| L3 | 存储引擎 | Fuzz 测试应验证的不变式列表不完整。 | 补充：搜索路径正确性、tombstoneCount+非Tombstone=Count、层级排序、树高度回收、无孤儿页面。 |
| L4 | 存储引擎 | VersionChain GC 与 Compaction 双层清理的耦合关系未文档化。 | 增加跨层关系图，展示 Tombstone 从 BTree 页面到 VersionChain 的清理路径。 |

| L6 | Go 并发 | Merge 成功后原页面的 `PageRef.Release()` 需显式调用，否则 refCount 泄漏。 | MergeLeaves 成功后对原 left/right 的 PageRef 调用 Release。 |
| L7 | DDD | mergeRoot 前应检查子节点 `NodeState` 是否为 Splitting/Merging，避免将中间态的节点提升为根。 | mergeRoot 入口处增加子节点状态校验，或使用重试机制。 |

### 7.5 评审结论

| 维度 | 评分 | 说明 |
|------|------|------|
| 整体设计方向 | 7.5/10 | Lazy Merge + Compaction 是 B+Tree 空间回收的经典策略，与现有 COW + CAS 模式一致 |
| 并发安全 | 5.0/10 | Merge 双页面 CAS、parent 传播竞争、TombstoneCount 原子性三个关键缺口需补 |
| 分层架构 | 6.0/10 | PageHeader 污染 + BTreeStorage 胖接口两个 CRITICAL 需重构 |
| 实施可行 | 7.0/10 | 4 步实施计划合理，但 Step 1 前需先解决 C1-C6 |
| 加权平均 | **6.4/10** | |

**核心改进方向**：
1. **Merge 的并发模型需重新设计**：不能简单套用 Split 的对称模式，双页面操作 + RemoveChild 传播需要独立的并发保护
2. **TombstoneCount 维护需进入 COW 原子路径**：不能在 mutateFunc 之外单独调整
3. **分层边界需修正**：tombstoneCount 上提到 btree 层，PageMerger 提取为独立接口
