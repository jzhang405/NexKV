## 一、Phase 4.2: RestoreDiskChunkManager

> 目标：从已有 `.ao` 文件恢复 ChunkManager 状态（重启/崩溃恢复）
> 对齐：Lealone `ChunkManager.init()` 恢复协议
> 预计文件：`disk_chunk_manager.go`（新增函数）、`chunk_file.go`（readHeader 完善）

### 1.1 恢复协议（8 步）

```
RestoreDiskChunkManager(dir string) (*DiskChunkManager, error)

1. 扫描目录: os.ReadDir → 过滤 btree_*_*.ao → 解析文件名
2. 删除零长度文件（崩溃时创建但未写入）
3. 对每个文件:
   a. 正则 btree_(\d+)_(\d+)\.ao → chunkID + seq
   b. 追踪 maxSeq 及其对应的 chunkID
   c. 处理重复 chunkID: 保留最高 seq 的文件名（备份恢复场景）
4. 按 seq 升序排序所有 Chunk
5. 打开最高 seq 的 Chunk 作为 lastChunk
6. 验证双块头部（readHeader）:
   - 块 0 有效 → 解析头部
   - 块 0 损坏 + 块 1 有效 → 从副本恢复
   - 两块都损坏 → 标记为损坏，跳过（WARNING 日志）
7. 从头部恢复元数据: pageCount, removedPages, pagePosToLen
8. 重建内存结构: chunkIDs BitSet, idToChunk, chunks 切片
```

### 1.2 新增函数

```go

// recoverFromHeader 从 header 恢复 chunk 的元数据映射
func (cm *DiskChunkManager) recoverFromHeader(c *ChunkFile, h *ChunkHeader) error
```

### 1.3 需要修改的现有代码

| 文件 | 变更 |
|------|------|
| **`chunk_file.go:ChunkFile`** | **恢复 `seq uint64` 字段**（Phase 4.1 简化时删除，Phase 4.2 恢复排序必需） |
| **`disk_chunk_manager.go:DiskChunkManager`** | **恢复 `seqToID map[uint64]uint32`**（恢复时从 seq 反查 chunkID） |
| **`disk_chunk_manager.go:createChunk`** | 填充 `c.seq = cm.maxSeq` 和 `cm.seqToID[seq] = chunkID` |
| `chunk_file.go:readHeader` | 移除 `//nolint:unused`，完善错误路径 |
| `chunk_header.go:parse*` | ✅ 已修复 — 所有 parse* 函数已正确返回 error，无静默吞错 |
| `chunk_file.go:openChunkFile` | ✅ 无需改动 — O_RDWR 已满足恢复+写入需求，无需 O_RDONLY |
| `disk_chunk_manager.go:chunks` | 恢复时需支持从切片中移除损坏的 chunk（当前仅 `createChunk` append） |

> **设计决策**：Phase 4.1 的 code simplifier 删除了 `ChunkFile.seq`、`ChunkFile.path` 和 `DiskChunkManager.seqToID`（当时无读取路径）。Phase 4.2 恢复协议**必须恢复 `seq` 和 `seqToID`**，因为按 seq 排序是 Lealone 恢复协议的核心。`path` 可恢复也可不恢复（可从 `cm.dir + filename` 重建）。

## 二、Phase 4.3: WAL-AO 集成

> 目标：Checkpoint 时将 mmap 脏页序列化到 AO 文件，建立 pageID→ChunkPosition 映射
> 前置：Phase 4.2 完成

### 2.1 集成点

```
Checkpoint 时序（Fuzzy Checkpoint）:

T1: WAL 记录当前 LSN (checkpointStartLSN)
T2: BTree.EnumeratePages(rootRef) 后序遍历
     ├─ 子页面排在父页面之前（Children-First 语义）
     └─ 输出 []PageFlushItem
T3: 对每个 PageFlushItem:
     ├─ ChunkPos == 0（脏页）→ cm.Allocate + cm.WritePage
     └─ ChunkPos != 0（已持久化）→ 跳过
T4: cm.Sync() — 所有 chunk 文件 fsync
T4a: pageLocs 批量更新（AO Sync 后、WAL Append 前）
T5: WAL.Append(CheckpointEntry) — checkpointStartLSN + rootPageID + pageLocs
T6: WAL.Sync()
T7: WAL.Truncate(checkpointStartLSN) — 丢弃已持久化的旧 WAL

兼容性说明:
  Phase 3 的 recovery.go 硬编码 len(e.Key) == 8 检查会拒绝 Phase 4 的扩展 Key（含 pageLocs）。
  解决方案:
    a. Phase 4 注册新的 WALTypeCheckpointV2 类型码
    b. Recovery 先尝试 len(e.Key) >= 8+8+4 解析 Phase 4 格式，失败则回退 Phase 3 格式
    c. 详见原始 spike 文档 §5.2 和 §6.4.1
```

#### (D) CheckpointManager 集成

**类型兼容性注意**：当前 `checkpoint.Manager` 使用私有接口 `WALWriter`（具有自己的 `LSN` 和 `WALEntry` 类型），而非 `service.WAL`。`DiskWAL` 实现了 `service.WAL`（基于 `wal.LSN`/`wal.WALEntry`），但 `checkpoint.LSN`、`checkpoint.WALEntry` 和 `wal.LSN`、`wal.WALEntry` 是**不同的类型**。Phase 4.3 需选择：

- 选项 A：将 checkpoint 的 `WALWriter` 接口迁移为使用 `service.WAL`（推荐，统一类型体系）
- 选项 B：创建从 `service.WAL` 到 `WALWriter` 的适配器
- 选项 C：让 `DiskWAL` 同时实现两个接口

```go
// 推荐最终形态（选项 A）:
type Manager struct {
    wal        service.WAL              // 统一接口
    btree      BTreeScanner
    cm         service.ChunkManager     // Phase 4 新增
    serializer *chunk.PageSerializer    // Phase 4 新增
}

func (m *Manager) FuzzyCheckpoint() error
```

### 2.3 惰性加载路径

```
读取流程:
  GetLeafPage(pageID):
    1. page := pm.PageIDToPtr(pageID)
    2. if page is valid → return page  // 已在 mmap 缓存中
    3. pos, ok := pageLocs.Load(pageID)
    4. if !ok → return ErrPageNotFound
    5. rawPageID := pm.Alloc()          // 分配物理 mmap 页
    6. data := cm.ReadPage(pos)
    7. serializer.Deserialize(data, pm.PageIDToPtr(rawPageID))
    8. return page  // 惰性加载完成
```

- `FuzzyCheckpoint` 能将脏页写入 AO，pageLocs 映射正确
- 惰性加载：从未缓存的 pageID 可正确从 AO 恢复
- `go test -race` 通过，覆盖率 >= 80%

## 三、Phase 4.4: GC 集成

> 目标：WAL GC 与 Chunk 页回收联动
> 前置：Phase 4.3 完成

### 3.1 联动协议

```
WAL GC 触发条件（任一）:
  - Checkpoint 完成后自动触发 Truncate
  - 手动触发 / 定时 GC

GC 流程:
  1. FuzzyCheckpoint() 完成后 → cm.Sync() → WAL.Truncate(checkpointStartLSN)
  2. ChunkCompactor 异步运行:
     a. 收集所有 removedPages
     b. 计算每个 Chunk 的 fillRate
     c. 重写低填充率 Chunk 的活跃页面到新 Chunk
     d. 更新 PageRef 的 ChunkPos
     e. 删除旧 Chunk 文件
```

### 3.2 ChunkCompactor 实现（Phase 5 完整版）

当前 `chunk_compactor.go` 为 stub（`NeedCompaction()→false`, `Compact()→nil`）。Phase 4.4 需要：

| 函数 | 状态 | Phase 4.4 动作 |
|------|------|---------------|
| `NeedCompaction()` | stub | 实现 fillRate 检查 |
| `Compact()` | stub | 实现 Lealone 压缩算法（贪心选择+重写） |
| `executeCompact()` | 未定义 | 新增：主入口 |
| `getFillRate()` | 未定义 | 新增：填充率计算 `1 + 98*live/total` |

### 3.3 removedPages 全局化

Phase 4.1 中 `removedPages` 存储在 `ChunkFile` 级别（per-chunk map）。GC 需要全局视图：

```go
// 方案 A: 全局 removedPages 集合（对齐 Lealone ConcurrentSkipListSet<Long>）
type DiskChunkManager struct {
    // ...
    removedPages map[model.ChunkPosition]struct{} // 全局已删除页面集
}
```

### 3.4 验证标准

- Checkpoint 后 WAL Truncate 正确执行（旧 WAL 文件被清理）
- ChunkCompactor 能识别低填充率 Chunk
- 压缩后活跃页面在新 Chunk 中可读
- `go test -race` 通过，覆盖率 >= 80%
