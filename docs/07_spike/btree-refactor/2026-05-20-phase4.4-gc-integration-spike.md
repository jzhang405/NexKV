## 一、概述

Phase 4.3 完成后，FuzzyCheckpoint 将脏页写入 AO 并记录 pageLocs 到 WAL。但两个空间回收缺口仍然存在：

| 缺口 | 现象 | 解决 |
|------|------|------|
| **WAL 无限增长** | Checkpoint 后旧 WAL segment 占盘 | `WAL.Truncate(checkpointStartLSN)` — 已在 Phase 4.3 实现 |
| **AO 空洞积累** | FreePage 产生 removedPages，Chunk fillRate 下降 | **ChunkCompactor** — Phase 4.4 实现 |
| **removedPages 分散** | 每个 ChunkFile 各自维护 removedPages，无全局视图 | **全局 removedPages** — Phase 4.4 实现 |

## 三、ChunkCompactor 实现

### 3.1 当前 stub

```go
// chunk_compactor.go
func (c *ChunkCompactor) NeedCompaction() bool { return false }
func (c *ChunkCompactor) Compact() error       { return nil }
```

### 3.2 Lealone 压缩算法

对齐 Lealone `ChunkCompactor.java`，9 步压缩：

```
executeCompact():
  1. 收集所有 removedPages（全局）
  2. 若 removedPages 为空 → 直接返回
  3. 遍历所有 Chunk，跳过 NodePage
  4. 计算每个 Chunk 的 fillRate = 1 + 98 × livePageLength / totalPageLength
  5. 分类:
     - fillRate == 0 → unusedChunks（可直接删除）
     - fillRate <= minFillRate → rewritable（需重写活跃页）
  6. 按 (fillRate 升序, sumOfLivePageLength 升序) 排序
  7. 贪心选择: 累计 liveSize <= MAX_REWRITE_SIZE
  8. 将选中 Chunk 的活跃页面写入新 Chunk
  9. 两阶段删除:
     a. 先标记 unusedChunks
     b. 新 chunk Sync 成功后 → os.Remove 物理删除旧文件
```

### 3.3 接口变更

```go
type ChunkCompactor struct {
    cm          *DiskChunkManager

}

// NeedCompaction 返回是否有低填充率 Chunk 需要压缩。

func (c *ChunkCompactor) Compact() error

// 新增方法

```

### 3.4 fillRate 计算

```go
// getFillRate 对齐 Lealone: 1 + 98*live/total
// fillRate=1 表示"空"（可以被完全回收）
// fillRate=100 表示"满"（所有页面都是活跃的）
func (c *ChunkCompactor) getFillRate(cf *ChunkFile) int {
    var totalLen, liveLen int64
    for pos, length := range cf.pagePosToLen {
        totalLen += int64(length)
        if _, removed := cf.removedPages[pos]; !removed {
            liveLen += int64(length)
        }
    }
    if totalLen == 0 {
        return 1
    }
    return 1 + int(98*liveLen/totalLen)
}
```

## 四、全局 removedPages

### 4.1 当前状态

```go
type ChunkFile struct {
    removedPages map[model.ChunkPosition]struct{} // per-chunk
}
```

`FreePage` 将位置写入 `c.removedPages`（per-chunk 级别）。

### 4.2 方案：DiskChunkManager 全局 removedPages

```go
type DiskChunkManager struct {
    // ... 现有字段 ...
    removedPages map[model.ChunkPosition]struct{} // 全局已删除页面集
}
```

**FreePage 修改**：
```go
func (cm *DiskChunkManager) FreePage(pos model.ChunkPosition) error {
    // ... existing lookup ...
    c.removedPages[pos] = struct{}{}      // per-chunk (保留，用于 fillRate)
    cm.removedPages[pos] = struct{}{}     // 全局 (用于 Compactor 扫描)
    return nil
}
```

**ChunkCompactor 扫描**：
```go
func (c *ChunkCompactor) collectRemovedPages() map[model.ChunkPosition]struct{} {
    cm.mu.RLock()
    defer cm.mu.RUnlock()
    result := make(map[model.ChunkPosition]struct{}, len(cm.removedPages))
    for pos := range cm.removedPages {
        result[pos] = struct{}{}
    }
    return result
}
```

## 六、与 Phase 6.5 的关系

| 关注点 | Phase 4.4 | Phase 6.5 |
|--------|-----------|-----------|
| **范围** | Chunk 级别空间回收 | Page 级别 Merge/Borrow |
| **输入** | removedPages (ChunkPosition) | Tombstone entries (PageID) |
| **操作** | 重写低填充率 Chunk | 合并低填充率 BTree 页面 |
| **输出** | 删除旧 .ao 文件 | 回收 mmap 页面 |
| **共享** | ChunkCompactor 框架 | — |

Phase 4.4 的 ChunkCompactor 是 **AO 文件级别的垃圾回收**——处理的是整个 .ao 文件。Phase 6.5 处理的是 **BTree 页面级别的空间回收**——合并相邻的稀疏页面。两者互补：Phase 4.4 回收删页后的 Chunk 空间，Phase 6.5 回收删除 key 后的 Page 空间。

## 七、风险与缓解

| 风险 | 缓解 |
|------|------|
| 压缩期间 Chunk 被并发写入 | 压缩目标为 fillRate <= 30% 的冷 Chunk，lastChunk 不参与压缩 |
| 重写时活跃页面被 FreePage | 重写前 Retain 活跃页面，重写后释放 |
| 两阶段删除中 Crash | 新 Chunk Sync 成功后才删除旧文件；Crash 后 Recovery 跳过孤立旧文件 |
| 全局 removedPages 内存增长 | `Compact()` 完成后 `delete(removedPages, pos)` 清理 |
