| 步骤 | 描述 | 状态 |

**核心缺口**：header 解析通过后，`pagePosToLen` 和 `removedPages` 初始化为空 map（line 435-436）。实际页面元数据存储于 chunk body 中，需要通过 `PagePositionAndLengthOffset` 和 `RemovedPageOffset` 反序列化恢复。

**缺口根因**：这些元数据由 Phase 4.3 的 `FuzzyCheckpoint` 流程写入。Phase 4.2 时 chunk body 还没有页面数据，所以恢复只能读到 header。

## 二、当前设计约束

### 2.1 页面数据写入时机

当前 Checkpoint 流程（`checkpoint/checkpoint_manager.go`）只检查 `ChunkPos`：

```go
// checkpoint_manager.go:FuzzyCheckpoint
if page.ChunkPos == 0 {
    // 新页/脏页 → cm.Allocate + cm.WritePage
} else {
    // 已持久化 → 跳过
}
```

问题是：**pagePosToLen 和 removedPages 在 ChunkManager 内存中维护，但从未序列化到 .ao 文件**。Close 时 `writeHeader` 填充了这些字段，但它们的**实际数据**没有写入文件——只有 header 文本写入了。

### 2.2 ChunkHeader 的序列化范围

`ChunkHeader` 有 `PagePositionAndLengthOffset` 和 `RemovedPageOffset` 字段，但：
1. **写入时**：encode() 输出这些字段，但值是 0（`Close()` 在 `disk_chunk_manager.go:243-258` 填充了 SumOfLivePageLength 等，但**没有填充 offset 字段**）
2. **读取时**：decodeHeader() 解析这些字段，但 recovery 忽略了它们的值

## 三、最小实现方案

### 决策 1：Phase 4.2 做什么

**不等到 Phase 4.3**。Phase 4.2 完成 "header 恢复即可用" 的标准——即恢复后 `DiskChunkManager` 可以正常执行 `Allocate`、`WritePage`、`FreePage`、`ReadPage`。

具体含义：
- `pagePosToLen` 直接重建：通过扫描 chunk body 中的每个 PageFrame header 恢复
- `removedPages` 直接重建：通过检查 PageFrame header 中的 `deleted` 标记恢复
- 不依赖 `PagePositionAndLengthOffset` / `RemovedPageOffset`（这两个字段延后到 Phase 4.3 正式支持）

### 决策 2：PageFrame 扫描恢复（修正格式）

**实际格式**（`page_serializer.go:Serialize`）：

```
PageFrame = [CRC32C:4][pageData:pageLength]
pageLength = MinPagePayload(56) ~ MaxPagePayload(4096)
帧总长 = 4 + pageLength = 60 ~ 4100 字节
```

CRC32C 覆盖 `pageData` 部分（不含 CRC 自身）。帧中**不存储** pageLength ——调用方通过 `pagePosToLen` 外部维护。

**当前 Checkpoint 行为**（`btree.go:168`）：所有页面以 `MaxPagePayload` (4096) 序列化，帧固定 4100 字节。

**Phase 4.2 扫描策略**：
1. 固定步长 4100 字节（`MaxDiskPageSize`）
2. 每步读取 4100 字节，校验 CRC32C on `data[4:4100]`
3. 校验通过 + pageType 有效 → 有效帧，记录 `pagePosToLen[pos] = 4100`
4. 校验失败 → 该帧损坏，**不 break**，继续下一个 4100 步长（单个坏帧只丢一帧）

> **约束**：此方案只识别 `MaxPagePayload` 帧。若未来引入变长帧（小页面只序列化 header），扫描将遗漏这些帧。Phase 4.3 的 header offset 恢复会替代此扫描路径。Phase 4.2 的扫描代码保留为**向后兼容 fallback**——Phase 4.3 优先读 header offset，旧 chunk（无 header offset）回退扫描。

### 决策 3：removedPages 恢复为空

`page_serializer.go` 格式中不存储 removed 标记。

**选择**：Phase 4.2 不恢复 removedPages（初始化为空），Phase 4.4 通过 header offset 恢复。

这是保守安全的——所有页面被视为 "live"，GC 延迟但无数据丢失风险。**已知风险**：恢复后到 Phase 4.4 之间的 delete 操作产生的 `FreePage` 不会被 GC 回收，chunk 可能暂时膨胀。

## 四、实现计划

### Step 1: scanPageFrames — 固定步长 CRC32C 扫描

```go
// chunk_file.go 新增

// scanPageFrames walks the chunk body at fixed stride (MaxDiskPageSize=4100)
// and rebuilds pagePosToLen by CRC32C verification.
// Assumes all pages are serialized with MaxPagePayload (current Checkpoint behavior).
// Frame format: [CRC32C:4][pageData:4096]
func (c *ChunkFile) scanPageFrames() (map[model.ChunkPosition]int32, error) {
    result := make(map[model.ChunkPosition]int32)
    buf := make([]byte, MaxDiskPageSize) // 4100 bytes

    const maxConsecutiveMiss = 16 // early-exit: N consecutive CRC failures → end of data
    consecutiveMiss := 0

    for offset := int64(ChunkHeaderSize); offset+MaxDiskPageSize <= c.capacity; offset += MaxDiskPageSize {
        _, err := c.file.ReadAt(buf, offset)
        if err != nil {
            break
        }

        expected := binary.LittleEndian.Uint32(buf[0:CRCSize])
        actual := wal.CRC32C(buf[CRCSize:])
        if expected != actual {
            consecutiveMiss++
            if consecutiveMiss >= maxConsecutiveMiss {
                break // reached zero-fill tail of preallocated file
            }
            continue
        }

        pageType := buf[CRCSize+offheap.PageTypeFieldOffset]
        if pageType != offheap.PageTypeIndex && pageType != offheap.PageTypeLeaf {
            consecutiveMiss++
            if consecutiveMiss >= maxConsecutiveMiss {
                break
            }
            continue
        }

        consecutiveMiss = 0 // reset on valid frame
        pos, _ := model.EncodeChunkPosition(c.id, uint32(offset), 0)
        result[pos] = MaxDiskPageSize
    }
    return result, nil
}
```

**帧损坏容错**：单个坏帧 `continue` 不 `break`，仅丢失该帧，后续健康帧不受影响。CRC32C 碰撞概率 ~2.3×10⁻¹⁰/帧，pageType 二次校验进一步降低误判率。

**Early-Exit 优化**：chunk 文件通过 `preallocate` 预分配至 256MB，实际写入量可能远小于此。连续 N 帧（如 16 帧）CRC 失败即判定为数据尾，`break` 终止扫描——避免遍历完整的 256MB 零填充（~65,000 次 ReadAt）。

**pageType=0 占位的影响**：恢复后所有 frame 的 `ChunkPosition.PageType() = 0`（= `PageTypeIndex`）。当前 `ReadPage` / `FreePage` 不检查 PageType，所以不影响 Phase 4.2 功能。若未来 BTree 惰性加载路径依赖 PageType 区分子节点/叶子节点，需要 Phase 4.3 从 header 恢复正确的 pageType。Phase 4.2 标注此约束。

### Step 2: 集成到 RestoreDiskChunkManager

```go
// Step 7 修改: 从 header 恢复 → 从 PageFrame scan 恢复
c := &ChunkFile{
    id:           fe.chunkID,
    seq:          fe.seq,
    file:         f,
    capacity:     st.Size(),
    nextOffset:   ChunkHeaderSize,
    pagePosToLen: make(map[model.ChunkPosition]int32),
    removedPages: make(map[model.ChunkPosition]struct{}),
}

// 验证 header
if _, err := c.readHeader(); err != nil {
    f.Close()
    continue
}

// ★ Phase 4.2: 从 chunk body 扫描恢复 pagePosToLen
pageLens, scanErr := c.scanPageFrames()
if scanErr != nil {
    // 扫描失败不阻塞恢复——pagePosToLen 为空时 ReadPage 会返回 ErrPageNotFound
    // 上层惰性加载路径可通过 ReadPage 重试
}
c.pagePosToLen = pageLens
c.nextOffset = int64(ChunkHeaderSize)
for pos, l := range pageLens {
    if int64(pos.FileOffset())+int64(l) > c.nextOffset {
        c.nextOffset = int64(pos.FileOffset()) + int64(l)
    }
}
```

## 五、不做什么（Out of Scope）

| 事项 | 原因 |
|------|------|
| 恢复 `removedPages` | Phase 4.4 GC 集成时实现，当前初始化为空。风险：恢复后到 Phase 4.4 间的 delete 不被 GC 回收，chunk 可能暂时膨胀 |
| 填充 `RootPagePos` | 需要 BTree root 信息，延后到 Phase 4.3 Checkpoint。**影响**：恢复后 BTree 无法定位根节点——Phase 4.2 只恢复 ChunkManager 结构，BTree 的惰性加载路径需要 Phase 4.3 完成 Checkpoint 重建 pageLocs 后才有 RootPagePos |
| 修改 PageFrame 格式增加长度/removed 标记 | 最小改动原则，Phase 4.3 通过 header offset 管理 |
| 恢复 `LastTransactionID` / `MapSize` | Phase 4.3 Checkpoint 写入时填充 |

### 5.1 scanPageFrames 的向后兼容角色

Phase 4.3 引入 header offset 恢复后，`scanPageFrames` **不删除**——保留为 fallback 路径：

```
Phase 4.3 恢复时:
  if header.PagePositionAndLengthOffset != 0:
      // 新 chunk → 直接读 offset 反序列化 pagePosToLen
  else:
      // 旧 chunk（Phase 4.2 期间写入，无 header offset）→ scanPageFrames fallback
```

这样 scanPageFrames 不是过渡代码，而是向后兼容层。
