# Spike：BTree LOB（Large Object）溢出页方案

> **日期**：2026-06-09  
> **分支**：`spike/btree-lob`  
> **参考**：[[2026-06-09-lob-scheme-investigation]] — Lealone LOB 方案深度调查  
> **背景**：当前 NexKV BTree 每条 record 必须在 4KB 单页内存储。MVCC value 约 50B，页面可存 ~80 entries。若 value 超过 ~3.9KB（4KB - header - MVCC header），insert 直接失败。

---

## 一、问题定义

### 1.1 当前限制

```
当前 MVCC 格式：
  [Flag:1][prevFlag:1][prevBeginTS:8][prevValLen:2][prevVal:N][beginTS:8][realVal:M]

  total = 12 + prevVal + 8 + realVal
  单页容量: 4096B - PageHeader(56B) - 1 entry slot(16B) = 4024B
  → prevVal=0 (Insert) 时, realVal ≤ 4024-12-8 = 4004B
  → Update 且 prevVal=50B 时, realVal ≤ 3954B

  value > 4004B → InsertLeafEntry 返回 page full → 整个操作失败
```

### 1.2 需求场景

- **大 Value 存储**：用户 value 可能 4KB ~ 1MB
- **稀疏大 Value**：99% key 的 value < 100B，1% key 的 value > 4KB
- **读写混合**：大 value 的读频率与小 value 相同

### 1.3 Lealone 方案

Lealone 在 `BTreeStorage` 层实现 LOB：
- 阈值 2KB → value 存储在溢出页链中
- BTree 叶子页存储 21B 的 LOB 引用（Flag:1 + Version:8 + FirstPageID:8 + Length:4）
- 溢出页：NextPageID:8 + ChunkSize:4 + Data:4084B
- 链式结构，按需分配，删除时沿链 free

**关键约束**：BTree 对 LOB **感知**（`BTreeStorage.isLargeValue`），非透明式。

## 二、NexKV LOB 方案设计

### 2.1 设计原则

与 Lealone 不同，NexKV LOB **对 BTree 完全透明**。BTree 只看到 `[]byte` value，不知道里面的内容。LOB 逻辑在 **Value 编码/解码层**（`mvcc` 包或新增 `storage/lob` 包）。

```
优势：
  - BTree 零改动（不需要 isLargeValue 判断）
  - MVCC 格式扩展自然（在现有 [beginTS][realVal] 中嵌入 LOB 引用）
  - 删除/回滚路径统一（BTree 只看到 value 替换）
```

### 2.2 存储格式

#### LOB Flag

新增 `FlagLOBNormal = 0x02`（区别于 `FlagNormal=0x00` / `FlagTombstone=0x01`）。

```
普通 value: [Flag:0x00][prevFlag][prevBeginTS][prevValLen][prevVal][beginTS][realVal]
LOB value:  [Flag:0x02][prevFlag][prevBeginTS][prevValLen][prevVal][beginTS][lobRefLen:2][lobRef:N]
             lobRef = [FirstPageID:4][TotalLen:4]
```

> Flag 0x02 已在 ParseMVCC/BuildMVCC 中保留（Phase 3 版本内嵌时已规划）。prev 字段仍正常使用（大 value 的旧版本如果也是 LOB，prev 字段包含 LOB ref）。

#### 溢出页面格式

```
Overflow Page (4KB):
  [NextPageID:4][ChunkSize:2][Reserved:2][Data:4088B]

  NextPageID=0 → 链尾
  ChunkSize   → 本页实际数据字节数（≤4088）
```

> NextPageID 用 uint32（页面上限 2^32 = 16TB，128GB mmap 下够用）。

### 2.3 LOB 读写流程

```
Write:
  BuildMVCC(flag=0x02, beginTS, lobRef, prevFlag, prevBeginTS, prevVal)
    → lobRef = [FirstPageID:4][TotalLen:4]
  BTree.Set(key, encoded)  ← BTree 无感知, 31B value 正常插入叶子页

Read:
  BTree.Get(key) → raw
  ParseMVCC(raw) → mv.Flag == 0x02 → mv.LOB.FirstPageID, mv.LOB.TotalLen
  lob.ReadPages(firstPageID, totalLen) → concatenated value
  返回 concatenated value

Delete:
  BTree.Delete → tombstone → 普通 Tombstone 写入叶子页
  LOB 页面回收：依赖 BTree epoch-based GC（页面被 Retire 后自动 free）
  LOB 链页面需单独 track → PageManager.AllocOverflow/FreeOverflow
```

### 2.4 页面分配

```
PageManager.AllocOverflow() → 分配单页（同 Alloc，但标记为 Overflow 类型）
  或一次性分配 N 页 → AllocOverflowChain(totalLen)
    1. 计算 N = ceil(totalLen / 4088)
    2. 分配 N 个页面
    3. 构建链表 (sort by PageID 升序，相邻页设置 NextPageID)
    4. 返回首页 ID
```

## 三、实现计划

### Step 1: MVCC LOB Flag + 编码 (~30行, mvcc/codec.go)

- 新增 `FlagLOBNormal = 0x02`
- `MVCCValue` 新增 `LOB *LOBRef` 字段
- `ParseMVCC`: flag==0x02 → 解析 lobRef
- `BuildMVCC`: flag==0x02 → 写入 [lobRefLen:2][lobRef:N]

```go
type LOBRef struct {
    FirstPageID uint32
    TotalLen    uint32
}

type MVCCValue struct {
    // ... existing fields
    LOB *LOBRef // nil for non-LOB values
}
```

### Step 2: 溢出页面 Alloc/Free (~50行, offheap/page_manager.go)

- `AllocOverflow(data []byte) (uint32, error)` — 分配溢出页链并写入数据
- `FreeOverflow(firstPageID uint32) error` — 沿链释放所有页面
- `ReadOverflow(firstPageID uint32, totalLen uint32) ([]byte, error)` — 沿链读取拼接

### Step 3: BTree 集成 (~20行, btree/btree.go)

- `BTree.Get` / `getRawBytes` — 解析出 LOB ref → `pm.ReadOverflow` → 返回完整值
- `BTree.Set` — 不需要改动（BuildMVCC 已在调用方编码好 LOB ref）
- `BTree.Delete` — 需要释放 LOB 页面链 → 解析旧值 → `pm.FreeOverflow`

```go
// In BTree.Get — after ParseMVCC:
if mv.LOB != nil {
    return b.storage.pm.ReadOverflow(mv.LOB.FirstPageID, mv.LOB.TotalLen)
}
```

### Step 4: MVCC 事务层集成 (~20行, mvcc/transaction.go)

- `SnapshotTx.Put`: value > 阈值 → 调用 `pm.AllocOverflow` → 存储 lobRef 到 WriteBuffer
- `SnapshotTx.Get` / `snapshotGet`: 解析 LOB ref → `pm.ReadOverflow` → 返回完整值
- `commitKey` / `rollbackOneKey`: LOB 页面生命周期管理

### Step 5: 阈值配置 + benchmark (~30行)

- `LOBSizeThreshold` 常量（默认 2048）
- benchmark: 大 value (4KB/64KB/1MB) 读写对比

## 四、与 Lealone 方案对比

| 维度 | Lealone | NexKV (本方案) |
|------|---------|----------------|
| LOB 感知层 | `BTreeStorage` | `MVCC codec` 层 |
| BTree 改动 | 需要 `isLargeValue` 判断 | **零改动** |
| 编码位置 | BTree 内部 | MVCC 编码层 |
| LOB Flag | 0x80 (1 byte) | 0x02 (复用 MVCC Flag) |
| 引用大小 | 21B (Flag+Version+ID+Len) | 10B (ID:4 + Len:4 + LobRefLen:2) |
| 溢出页数据 | 4084B (NextPage:8 + Size:4) | 4088B (NextPage:4 + Size:2 + Reserved:2) |
| 引用计数 | PageRef.refCount | Epoch-based GC |
| 删除 | BTree 自动处理 | 需要 Get old value → free LOB pages |
