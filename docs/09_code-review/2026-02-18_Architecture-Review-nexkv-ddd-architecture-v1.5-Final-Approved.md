## 三、v1.5 修订验证清单

### 5个批准条件（全部完成）

#### 条件 1：调整 P0 性能目标 ✅

**要求**：从 500K 调整到 300K ops/sec（基于 Badger 基线）

**理由**：
- Bf-Tree 移植风险高，先以 Badger 性能作为基线更稳妥
- P0 目标应基于已验证的技术（Badger），而非未移植的技术（Bf-Tree）

**修订验证**：
- [x] ✅ 1.2 核心目标：P0≥30万/P1≥50万/P2≥75万 ops/sec
- [x] ✅ 5.2 性能基准测试：P0 单节点写入 ≥ 30万 ops/sec
- [x] ✅ 5.3 性能验证计划：M2 单机性能 P0 ≥ 30万 ops/sec
- [x] ✅ 4.1 里程碑时间表：M2 性能达标（P0≥30万 ops/sec）
- [x] ✅ 4.2 Bf-Tree 移植计划：Week 8 检查点（30万 ops/sec）
- [x] ✅ 6.2 决策 1：Week 8 检查点（30万 ops/sec）

---

**要求**：3天培训（DDD + Go 泛型 + libp2p + Bf-Tree）

**理由**：
- 团队学习曲线陡峭（DDD + Go 泛型 + libp2p + Bf-Tree）
- 需要前期培训统一技术理解，降低开发风险

**修订验证**：

- [x] ✅ 2.3 Phase 规划：Week 0（3天）详细培训内容
  - Day 1 上午：DDD 架构原则（0.5天）
  - Day 1 下午：Go 泛型编程（0.5天）
  - Day 2-3：libp2p 基础（1天）
  - Day 4-5：Bf-Tree 原理（1天）
- [x] ✅ 4.1 里程碑时间表：新增 M0 里程碑（第0周）
- [x] ✅ 4.2 Bf-Tree 移植计划：Week 0 培训先行
- [x] ✅ 7.1 立即行动：Week 0 培训详细计划（Day 1-5）
- [x] ✅ 验收标准：培训签到、资料归档、测试通过率 ≥ 80%

#### 条件 3：优化 POC 验证 ✅

**要求**：Week 1-2 核心 POC，Week 3-4 扩展验证

**理由**：
- 当前 POC 与开发并行可能影响质量
- 需要分阶段验证，先验证核心功能，再验证扩展功能

**修订验证**：
- [x] ✅ 2.3 POC 验证策略：分为 Week 1-2 核心 POC 和 Week 3-4 扩展 POC
  - **Week 1-2 核心 POC**：
    - mDNS 节点发现（局域网）
    - 节点间直连通信
    - RPC 调用（延迟 < 5ms）
    - 验收标准：核心功能单元测试通过
  - **Week 3-4 扩展 POC**：
    - 3 节点集群通信
    - 性能基准测试（吞吐量 ≥ 10K ops/sec）
    - 连接建立时间（< 2秒）
    - 验收标准：M1 里程碑通过
- [x] ✅ 7.1 立即行动：Week 1-2 核心 POC + Week 3-4 扩展 POC

---
