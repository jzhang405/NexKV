## 📋 文档概述

本讨论文档针对 `2026-03-07-spike-percore-runloop-optimization.md` 中提出的优化方案进行可行性分析，邀请团队评审和讨论。

**方案核心**：将当前的 Task-per-Operation 模式优化为 RunLoop + Channel 模式，以减少 futex 调度开销和内存分配。

---

## 🎯 核心问题分析

### 当前实现的性能瓶颈

| 瓶颈 | 时间 | 占比 | 根因 |
|------|------|------|------|
| **futex 调度** | ~7,000 ns | **72.6%** | goroutine 调度开销 |
| WaitGroup 同步 | ~1,700 ns | 17.8% | 任务完成通知 |
| 实际执行 | ~930 ns | 9.59% | 业务逻辑 |
| Task 创建 | ~460 ns | 4.7% | channel + atomic 分配 |

**单操作延迟**: 9,674 ns vs 同步 103 ns (**慢 93.9x**)

### 优化目标

| 指标 | 当前实现 | RunLoop 优化 | 目标提升 |
|------|---------|-------------|---------|
| 单次延迟 | ~9,674 ns | **~5,000-8,000 ns** | **~2x** |
| 内存分配 | ~348B/任务 | **~16B/任务** | **~20x** |
| 吞吐量 | 24.4K ops/s | **~50K ops/s** | **~2x** |

### 讨论点 2：架构复杂度 vs 收益 ⭐⭐⭐⭐

**问题**：引入 RunLoop 模式是否会过度增加系统复杂度？

**当前架构**：
- Task-per-Operation 模式：简单、通用、可组合

**优化后架构**：
- 混合模式：Task + RunLoop + 智能路由
- Pipeline 链式架构（第 12 章）

**复杂度增加点**：
1. 双 API 模式（函数式 + 结构化）
2. 智能路由策略
3. 优先级调度（10 个 channel）
4. 混合模式管理

**需要讨论**：
- [ ] 是否可以简化设计？（如移除优先级 channel 数组）
- [ ] 是否真的需要智能路由？
- [ ] Pipeline 架构是否必要？可以先做基础 RunLoop 优化吗？

---

### 讨论点 3：长任务阻塞风险 ⭐⭐⭐⭐

**问题**：RunLoop 模式下，长任务是否会阻塞整个 Worker？

**风险场景**：
```go
// 短任务期望
func (t *BfTree) Get(key []byte) {
    // 预期: <10μs
}

// 长任务风险
func (t *BfTree) BatchGet(keys [][]byte) {
    // 可能: >1ms，阻塞 RunLoop
}
```

**缓解措施（文档提出）**：
1. 智能路由：短任务用 RunLoop，长任务用 Task 模式
2. 超时机制
3. 队列大小限制

**需要讨论**：
- [ ] 智能路由的阈值（10μs）是否合理？
- [ ] 如何准确预估任务执行时间？
- [ ] 是否需要手动标记长短任务？

---

### 讨论点 4：Pipeline 链式架构 ⭐⭐⭐⭐⭐

**问题**：第 12 章提出的 Pipeline 架构是否必要？是否过度设计？

**Pipeline 架构**：
```
kv-write-req --channel--> kvapi core
    --(create)--> btree-write-req --channel--> btree core
    --(create)--> wal-write-req --channel--> wal core
    --(create)--> disk-write-req --channel--> disk write core
```

**优势**：
- 完全异步，无阻塞
- 零拷贝，指针传递
- 天然背压

**复杂度**：
- 多个 RunLoop Worker 协调
- Channel 链路管理
- 错误传播和恢复

**需要讨论**：
- [ ] Pipeline 是否应该作为独立的 spike？
- [ ] 是否可以先完成基础 RunLoop，再考虑 Pipeline？
- [ ] Pipeline 的维护成本是否可控？

## 🎯 建议的实施路径

### 选项 A：渐进式实施（推荐）⭐⭐⭐⭐⭐

```
阶段 1: 最小可行验证 (2-3天)
├─ 实现 RunLoopWorker 基础结构
├─ 只支持 Get 操作
├─ 单一 channel（无优先级）
└─ 性能对比测试

↓ 验证通过

阶段 2: 完整功能实现 (3-5天)
├─ 支持所有操作（Get/Set/Delete/Batch）
├─ 优先级调度（可选）
├─ 智能路由（可选）
└─ 集成到 BfTree

↓ 稳定运行

阶段 3: Pipeline 架构 (独立 spike)
└─ 作为独立的架构升级项目
```

**优点**：
- 风险可控，每个阶段都可以独立验收
- 可以根据阶段 1 的结果决定是否继续
- Pipeline 架构独立，不影响基础优化

---

### 选项 B：完整实施（高风险）⭐⭐

```
一次性实施所有功能（包括 Pipeline）
├─ RunLoop 优化
├─ 优先级调度
├─ 智能路由
└─ Pipeline 架构
```

**缺点**：
- 风险高，一次性改动太大
- 难以定位性能问题的来源
- 实施周期长（10+ 天）

---

### 选项 C：暂缓实施 ⭐⭐⭐

**理由**：
- 当前性能是否真的是瓶颈？
- 是否有其他更简单的优化方案？
- 是否可以先优化其他模块（如 BfTree 本身）？

**建议**：
- 先进行性能分析，找出真正的瓶颈
- 评估其他优化方案（如批量 API）
- 重新评估优先级
