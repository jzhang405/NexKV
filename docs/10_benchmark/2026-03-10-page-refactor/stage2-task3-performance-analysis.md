## 🔍 性能回归分析

### 为什么有 10% 的性能差异？

**原因分析**：

1. **分支预测失败** (~5%)
   ```go
   if rootNode.PageID == 0 {
       return b.findPathDirect(key)  // 分支预测失败
   }
   ```
   - PageID == 0 检查
   - CPU 分支预测器需要适应

2. **函数调用开销** (~3%)
   ```go
   return b.findPathDirect(key)  // 额外的函数调用
   ```
   - 间接函数调用
   - 栈帧创建/销毁

3. **代码路径差异** (~2%)
   - FindPathPageID 有额外的 PageID 检查逻辑
   - 但实际路径相同（都调用 findPathDirect）

### 为什么内存开销相同？

```
Direct:  40 B/op, 2 allocs/op
PageID:  40 B/op, 2 allocs/op
```

**原因**：
- ✅ 两种方法最终都使用 `AcquirePath()`
- ✅ Path 池复用机制相同
- ✅ 没有额外的内存分配

## 🎯 性能优化空间

### 当前优化空间

1. **内联优化** (预计 -5%)
   ```go
   // 将 FindPathPageID 内联到 FindPath
   func (b *BTree) FindPath(key []byte) (Path, error) {
       if b.root.PageID == 0 {
           return b.findPathDirect(key)
       }
       return b.findPathPageID(key, b.root.PageID)
   }
   ```

2. **分支预测优化** (预计 -3%)
   ```go
   // 使用 likely/unlikely 提示
   if likely(b.root.PageID == 0) {
       return b.findPathDirect(key)
   }
   ```

3. **统一入口** (预计 -2%)
   - 在编译时选择模式，而非运行时
