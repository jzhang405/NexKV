## 关键发现

### ❌ 分裂策略优化失败

**增加 MaxKeys 反而降低性能**，与预期完全相反。

**性能下降幅度**:
- 写延迟增加 **63%** (5.04 µs → 8.18 µs)
- 内存分配增加 **107%** (17.9 KB → 37.1 KB)
- 读延迟增加 **18%** (179 ns → 212 ns)

---

## 失败原因分析

### 1. 内存复制开销增加

**问题**: 更大的节点 = 每次 Clone 复制更多数据

**数据**:
- C0: 17928 B/op (约 17.5 KB/次)
- C1: 37140 B/op (约 36.3 KB/次)
- **增加**: 107%

**分析**:
- Node.Clone 需要复制 Keys 和 Values 切片
- MaxKeys 512 的节点容量是 MaxKeys 256 的 2 倍
- 即使实际存储的键值对相同，切片底层数组仍然分配 2 倍空间

### 2. 缓存不友好

**问题**: 更大的节点导致 CPU 缓存命中率下降

**分析**:
- L1 缓存通常 32-64 KB
- C0 节点约 17.5 KB，可容纳 1-2 个节点
- C1 节点约 36.3 KB，只能容纳 1 个节点
- **缓存行替换更频繁**，导致性能下降

### 3. 测试场景不匹配

**问题**: 当前测试场景（数据量少）无法体现分裂频率降低的优势

**分析**:
- 基准测试运行时间短（10 秒）
- 总写入次数约 150 万次（1508143 ops）
- 按 MaxKeys 256 计算，分裂次数约 5859 次（1508143 / 256）
- 按 MaxKeys 512 计算，分裂次数约 2945 次（1508143 / 512）
- **分裂次数减少约 50%**，但节省的分裂开销不足以抵消增加的复制开销

### 4. 复制开销 vs 分裂开销

**权衡分析**:

**C0 (MaxKeys=256)**:
- 每次写入复制开销: 17.5 KB
- 分裂频率: 每 256 次写入分裂 1 次
- 平均开销: 17.5 KB + (分裂开销 / 256)

**C1 (MaxKeys=512)**:
- 每次写入复制开销: 36.3 KB
- 分裂频率: 每 512 次写入分裂 1 次
- 平均开销: 36.3 KB + (分裂开销 / 512)

**结论**: 复制开销增加（+18.8 KB）远大于分裂频率降低带来的收益。

## 启示

### 1. MaxKeys 不是越大越好

**传统观点**: 更大的节点 = 更少的分裂 = 更好的性能

**实际情况**: 存在权衡点，超过阈值后性能反而下降

**建议**:
- MaxKeys=256 可能已经是较好的权衡点
- 进一步增加需要考虑：
  - 内存复制开销
  - CPU 缓存命中率
  - 实际工作负载特征

### 2. 优化方向调整

**废弃优化**: 分裂策略优化（MaxKeys 256→512）

**替代方案**:
1. **对象池优化**（优先级提升至 P0）
   - 减少 Node 对象分配
   - 减少 GC 压力
   - 预期收益：写延迟 -15%, 内存分配 -60%

2. **其他优化方向**
   - 批量写入优化
   - 值指针方案（ValueRef）- Phase 2 考虑
   - 并发写入优化 - Phase 3 考虑
