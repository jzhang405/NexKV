# 1M Keys 性能验证报告

> **测试日期**：2026-03-17
> **测试目的**：验证 1000 keys 瓶颈分析的准确性
> **测试场景**：1M keys 初始化 + 100K Set 操作（纯内存模式）

---

## 📊 执行摘要

### 测试结果对比

| 指标 | 1000 keys | 1M keys | 变化 |
|------|-----------|---------|------|
| **吞吐量** | 187K ops/sec | 171K ops/sec | **↓ 8.5%** ⚠️ |
| **延迟** | 5.34 μs/op | 5.84 μs/op | **↑ 9.4%** ⚠️ |
| **样本数** | 533 | 3101 | **↑ 5.8x** ✅ |
| **数据大小** | ~10 MB | ~10 GB | **↑ 1000x** |

### 关键发现

1. **样本量更准确**：1M keys 测试收集了 3101 个样本（vs 533），统计分析更可靠
2. **性能下降明显**：1M keys 下性能下降 8.5%，说明数据规模对性能有显著影响
3. **应用层占比更低**：应用层函数从 2.5% → 0.88%，证明 **GC 是真正的瓶颈**
4. **defer 开销更高**：tryDeferToSpanScan 从 6.90% → 8.58%（+24.3%）

## 2. 性能下降原因分析

### 2.1 吞吐量下降 8.5%

**原因**：
1. **树深度增加**：1000 keys → 3 层，1M keys → 4-5 层
2. **页面分裂**：更多页面导致更多分裂操作
3. **GC 压力**：10GB 数据 vs 10MB 数据，GC 工作量大幅增加
4. **缓存未命中**：更大的数据集导致 CPU 缓存未命中增加

### 2.2 延迟增加 9.4%

**原因**：
1. **搜索路径更长**：4-5 层 vs 3 层
2. **更多页面加载**：虽然纯内存，但更多 PageInfo 需要访问
3. **GC 暂停**：更大的堆导致更长的 GC 暂停

### 2.3 defer 开销增加 24.3%

**原因**：
1. **更多函数调用**：树深度增加，调用链更长
2. **更频繁的 GC**：触发更多 defer 清理
3. **样本量增加**：更准确的统计显示 defer 开销更大

## 3. 优化建议更新

### 3.1 P0 优先级（立即实施）

| 优化项 | 预期提升 | 优先级 | 理由 |
|--------|---------|--------|------|
| **减少 defer 使用** | **15-20%** | **P0** | tryDeferToSpanScan 从 6.90% → 8.58% |
| **对象池复用** | 20-30% | P0 | 减少 GC 压力（仍然是主要瓶颈） |

### 3.2 P1 优先级（短期实施）

| 优化项 | 预期提升 | 优先级 | 理由 |
|--------|---------|--------|------|
| **减少树深度** | 10-15% | P1 | 5 层 → 3 层，减少搜索路径 |
| **批量 Set** | 10-20% | P1 | 减少 GC 触发频率 |
| **atomic.Value 优化锁** | 5-10% | P1 | GetParentRef 仍有一定占比 |

### 3.3 放弃的优化

| 优化项 | 原因 | 数据支持 |
|--------|------|----------|
| **优化 CloneShallow** | 应用层占比仅 1.1% | 1000 keys: 0.88% → 1M keys: 0.52% |
| **优化 CloneDeep** | 应用层占比仅 0.15% | 1000 keys: 0.73% → 1M keys: 0.15% |
| **优化 GetParentRef** | 应用层占比仅 0.16% | 1000 keys: 0.51% → 1M keys: 0.16% |

## 4. 结论

### 4.1 瓶颈分析准确性验证

| 之前结论 | 1M keys 验证 | 准确性 |
|---------|-------------|--------|
| **GC 是主要瓶颈（45-50%）** | GC 占 46% | ✅ **准确** |
| **应用层占 2.5%** | 应用层占 1.1% | ⚠️ **高估** |
| **tryDeferToSpanScan 占 6.90%** | 实际占 8.58% | ⚠️ **低估** |
| **CloneShallow 是热点** | 占比降至 0.52% | ❌ **不准确** |

### 4.2 关键洞察

1. **应用层优化空间有限**：1.1% CPU 占比，优化应用层函数意义不大
2. **GC 压力是核心问题**：46% CPU 时间消耗在 GC 上
3. **defer 开销被低估**：从 6.90% → 8.58%，defer 优化优先级提升
4. **数据规模影响显著**：1M keys 下性能下降 8.5%，需要考虑大数据集优化

### 4.3 优化方向调整

**之前方向**：优化应用层函数（CloneShallow, GetParentRef）

**调整后方向**：
1. **P0**：减少 defer 使用（最高优先级）
2. **P0**：对象池复用（减少 GC）
3. **P1**：批量 Set（减少 GC 频率）
4. **P1**：减少树深度（结构调整）
