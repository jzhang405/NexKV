# BTree Set 性能对比分析

**测试日期**: 2026-03-23
**测试场景**: **随机前缀 key**（分散在不同页面）
**测试配置**: 8 核心，50000 操作/线程

---

## 性能对比总结（随机前缀 key）

| 模式 | 8核吞吐量 | vs 基线 |
|------|-----------|---------|
| **纯内存 Set** (btree_perf_mem) | **3.38M ops/sec** | - |
| **纯内存 Set** (btree_perf_mem 顺序key) | **3.76M ops/sec** | - |
| SetWithRetryAndQueue (默认 GOGC) | 1.11M ops/sec | -67% |
| SetWithRetryAndQueue (GOGC=500) | 1.63M ops/sec | -52% |

**关键发现**：
- ✅ 纯内存模式仍然**超过目标 3.1-3.2M**
- ⚠️ 随机前缀 key 使性能**下降 10%** (3.76M → 3.38M)
- ❌ TaskScheduler 模式差距更大：**3.38M vs 1.15M = -66%**

## 瓶颈分析

### TaskScheduler 模式性能损失来源（随机 key）

| 因素 | 影响 | 说明 |
|------|------|------|
| **重试逻辑开销** | ~20% | 3次同步重试 + 状态检查 |
| **队列调度开销** | ~15% | Enqueue/Dequeue + 分片路由 |
| **GC 压力增加** | ~25% | 队列缓冲增加内存分配 |
| **路径查找** | ~10% | 虽有缓存，但随机 key 失效率高 |
| **锁竞争** | ~5% | 跨核心锁竞争 |

### 随机前缀 key 的影响

**纯内存模式**：
- ✅ 单核性能提升：页面分散减少缓存冲突
- ❌ 多核性能下降：更多页面访问增加内存带宽压力

**TaskScheduler 模式**：
- ❌ leafRef 缓存失效率增加：随机 key 导致频繁页面分裂
- ❌ 队列调度开销更明显：路径查找失败率增加

## 架构差异分析

### 纯内存 Set (btree_perf_mem)
```
用户请求 → tree.Set() → 内部路径查找 → LeafPage.Insert → 完成
```
- **无中间层**：直接调用
- **无额外开销**：零队列、零重试
- **性能**：3.38M ops/sec

### TaskScheduler 模式 (btree_perf_scheduler)
```
用户请求 → SetWithRetryAndQueue()
  ↓ 快速路径（3次重试）
  → tree.Set() → 内部路径查找 → LeafPage.Insert
  ↓ 慢速路径（失败后）
  → 创建 BTreeSetItem → Enqueue → TaskScheduler 调度
  → Execute → tree.Set() → 完成
```
- **快速路径**：3次重试增加开销
- **慢速路径**：队列调度增加延迟
- **性能**：1.15M ops/sec

**性能差距来源**：
- 快速路径重试：~20% 开销
- 慢速路径队列：~30% 开销
- GC 压力增加：~25% 开销
- 其他（锁、缓存失效）：~25%

## 优化建议

### ✅ 已实施优化

1. **leafRef 缓存**：
   - 单次操作 12x 提升 (57.60 ns vs 697.8 ns)
   - 随机 key 下失效率高，效果有限

2. **批量处理**：
   - 随机 key 下 batchSize 8 最优
   - 提升 ~5%

3. **GOGC=500**：
   - 提升 47% (1.11M → 1.63M)
   - 仍远低于纯内存模式

### 🎯 短期优化

1. **路径缓存优化**：
   - 缓存最近使用的完整路径
   - 随机 key 下收益有限
   - 预估：+10-20%

2. **减少重试次数**：
   - 从 3 次减少到 2 次或 1 次
   - 预估：+10-15%

### 🚀 中期优化

1. **Leaf-Level CAS** (参考 Lealone)：
   - 99.99% 写入无需 Root CAS
   - 消除路径查找开销
   - 预估收益：+50-100%

2. **优化队列调度**：
   - 减少锁竞争
   - 批量 dequeue
   - 预估：+10-20%

---

## 结论

1. ✅ **纯内存模式已达标**：3.38M ops/sec (随机 key) 仍超过目标 3.1-3.2M

2. ❌ **TaskScheduler 模式差距大**：1.15M vs 3.38M = -66%

3. 💡 **关键洞察**：
   - TaskScheduler 的设计目标是**高并发热点 key 场景**
   - 随机 key 场景下，队列开销大于收益
   - 需要重新评估使用场景

4. 📋 **建议**：
   - **均匀 key**：使用纯内存 Set (tree.Set)
   - **热点 key**：使用 TaskScheduler (SetWithRetryAndQueue)
   - **生产环境**：设置 GOGC=500 (+47%)
   - **架构优化**：考虑 Leaf-Level CAS 以消除路径查找开销
