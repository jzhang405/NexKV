| 并发度 | A: 中位数 (ops/s) | B: 中位数 (ops/s) | 变化 | B 扩展比 |

| 1T | 27,361 | 34,586 | **+26.4%** | 1.00x |

### 对比分析

1. **1T 提升 +26.4%**：消除 fmt.Sprintf 热路径开销的直接效果，单线程从 27K → 35K
2. **2T 出现波动**：Phase A 中 2T 中位数 44,774 偏高（一轮 54,953 拉高），Phase B 中有一轮 56,561 也说明 2T 最佳可达 56K+。锁竞争随机性导致中位数差异
3. **4T 提升 +60%**：预生成减少了每个 goroutine 的 CPU 占用，间接降低了锁碰撞频率
4. **8T 持平**：8 线程锁竞争是绝对瓶颈，fmt 优化无法改善

## 6. 瓶颈定位

### 6.1 锁竞争（主因，占 4T/8T 退化的 90%+）

- `setWithLeafLock` 使用 `TryLock()` 非阻塞锁
- 高并发下 TryLock 失败 → 返回 ErrRetry → 调用方重试
- 重试不做指数退避，busy-loop 浪费 CPU
- **4T/8T 的实际 CPU 利用率可能低于 50%**

### 6.2 分裂级联（次要）

- 叶子分裂时需要获取父节点锁
- 父节点满时需要获取祖父节点锁
- 自底向上加锁 → 多层锁竞争
- 分裂期间阻塞其他操作

### 6.3 原子计数器开销（次要）

- 每次 Set 成功调用 `successCount.Add(1)`
- 高并发下 atomic 操作本身有总线竞争

## 7. 优化路线图

### P0: 绕过 TaskScheduler 直通模式（已完成 ✅）

builtin 模式已直接调用 `BTree.Set`。

### P1: 测试工具 fmt.Sprintf 消除（已完成 ✅）

预生成 key/value 数组，单线程提升 +26%。

### P2: 指数退避重试策略（下一优先级）

当前 `Set` 使用固定重试（无退避）：
```go
// 当前：固定重试，无退避
for retries := 0; retries < maxRetries; retries++ {
    err := b.setWithLeafLock(ctx, key, value)
    if err == nil { return nil }
    // 立即重试 → 浪费 CPU
}
```

优化为指数退避：
```go
// 优化：指数退避，减少锁碰撞
for retries := 0; retries < maxRetries; retries++ {
    err := b.setWithLeafLock(ctx, key, value)
    if err == nil { return nil }
    if errors.Is(err, ErrRetry) {
        time.Sleep(time.Duration(1<<retries) * time.Microsecond)
    }
}
```

### P3: 分裂操作乐观并发（中期）

1. **先分裂再 CAS**：不加锁分裂，使用 CAS 更新父节点
2. **分段锁**：分裂期间只锁叶子节点，父节点更新使用乐观锁
3. **批量分裂**：积累多个需要分裂的叶子，一次性处理

## 8. 结论

1. **fmt.Sprintf 优化有效**：单线程 +26%（27K → 35K）
2. **锁竞争是核心瓶颈**：4T/8T 负扩展，与 fmt 无关
3. **下一步**：P2（指数退避）预期 4T 提升至 60K+ ops/s
4. **最终目标**：4 线程 80K+ ops/s，8 线程 120K+ ops/s
