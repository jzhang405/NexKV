## 背景

## 关键发现

### 1. 负扩展比严重，但 32T 均值回升

8T/16T 吞吐仅为 2T 的 13%~20%。32T 均值回升到 2T 的 56%，但这完全由两次「极快」(3.6M QPS) 拉高的——去掉这两个离群值后 32T 均值仅 644K，仍远低于 2T。

### 2. 慢组恒定 ~270K

无论 8/16/32 线程，「最慢组」的 QPS 都落在 ~270K-304K 附近。这暗示存在一个串行瓶颈，在最坏情况下将吞吐锁死在 ~270K。

### 3. 分群数随线程数增长

2T 单峰 → 8T/16T 双峰 → 32T 四峰。线程超订阅越严重，调度时序的微小差异被放大得越厉害。

### 4. 32T「极快组」超过 2T 单线程峰值

32T 极快组 3.6M QPS > 2T 均值 2.5M QPS。说明在运气极好的调度时序下，超订阅反而通过掩盖 mmap 延迟实现了超额吞吐——但这完全不可依赖。

### 5. 硬件超订阅

Apple M2 仅 8 核 (4P+4E)，8T 已跑满物理核心，16T/32T 严重超订阅。线程数越多，OS 调度器的线程切换时序越不确定，性能分布越分散。

### 三条铁证

**1. mmap 缺页排除**：所有轮次 major page faults = 0，page reclaims 恒定 ~47K-51K，与 QPS 完全无关。mmap 匿名映射全是软缺页（zero-fill pages），开销恒定。

**2. involuntary CS 与 QPS 强反相关**：慢轮 (245K QPS) 的 involuntary CS = 37,226，快轮 (658K QPS) = 7,550——差距 **5 倍**。线程频繁被内核强制抢占 CPU。

**3. voluntary CS 同样分化**：慢轮 3,255 vs 快轮 636（16T），差距 5 倍。线程在主动让出 CPU，符合 CAS/TryLock 失败后 yield 的模式。

## 瓶颈假设（更新）

**已排除**：
- ~~mmap 缺页风暴~~：page reclaims 恒定，major faults = 0
- ~~OS 物理页分配时序~~：缺页次数与 QPS 无关

**确认根因**：

1. **BTree PageLock 竞争 → 调度颠簸**（主要）：高并发下多个 goroutine 争抢同一 PageLock。TryLock 失败 → CAS 自旋 → 耗尽时间片 → 内核强制抢占 (involuntary CS) → 恶性循环。这是慢轮 involuntary CS 暴增至 37K+ 的直接原因。

2. **CAS 重试风暴放大效应**（次要）：`setDirect` 最多重试 10 次，并发时大量操作 CAS 失败后重试，消耗 CPU 但不产生进展。每次重试可能触发新的锁竞争 → 更多 CS → 更慢。

3. **调度时序决定快/慢分群**：第一轮锁竞争发生的时间点决定了整个 benchmark 的命运。如果 goroutine 碰巧错开锁争抢，几乎无 CS → 极快 (3.7M QPS)；如果同步争抢 → 连锁反应 → 慢 (245K QPS)。
