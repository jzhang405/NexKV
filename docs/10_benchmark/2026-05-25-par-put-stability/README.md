## 背景

`perf(btree): memory-mode performance optimization` (8ac3088) 之后，seq-put 从 1.0M QPS 提升到 3.4M QPS，但多线程 par-put 的稳定性未经充分验证。本测试在 2/8/16/32 线程下各跑 8 轮，评估 QPS 稳定性。

## 关键发现

### 1. 负扩展比严重，但 32T 均值回升

8T/16T 吞吐仅为 2T 的 13%~20%。32T 均值回升到 2T 的 56%，但这完全由两次「极快」(3.6M QPS) 拉高的——去掉这两个离群值后 32T 均值仅 644K，仍远低于 2T。

### 2. 慢组恒定 ~270K

无论 8/16/32 线程，「最慢组」的 QPS 都落在 ~270K-304K 附近。这暗示存在一个串行瓶颈，在最坏情况下将吞吐锁死在 ~270K。

### 3. 分群数随线程数增长

2T 单峰 → 8T/16T 双峰 → 32T 四峰。线程超订阅越严重，调度时序的微小差异被放大得越厉害。

### 4. 32T「极快组」超过 2T 单线程峰值

32T 极快组 3.6M QPS > 2T 均值 2.5M QPS。说明在运气极好的调度时序下，超订阅反而通过掩盖 mmap 延迟实现了超额吞吐——但这完全不可依赖。

### 5. 硬件超订阅

Apple M2 仅 8 核 (4P+4E)，8T 已跑满物理核心，16T/32T 严重超订阅。线程数越多，OS 调度器的线程切换时序越不确定，性能分布越分散。

## 瓶颈假设

1. **mmap 缺页风暴**：高并发写入时大量触发缺页中断，内核 mmap 写锁成为串行瓶颈
2. **BTree 内部锁竞争**：PageLock / CAS 重试在高并发下放大延迟
3. **OS 物理页分配时序**：哪个 goroutine 先触发缺页、内核批量分配策略，决定快慢分组
4. **Go 调度器与 mmap 交互**：goroutine 在缺页时被挂起，Go scheduler  steal work 的随机性放大了波动
